### 00:23–00:37 软件过程：瀑布模型与 Agile 概览

- 管理大项目首先要理解**软件过程**；今天只是总览，后续每周深入各阶段。
- **Q：期末考什么？** ——**没有期末考试**，唯一考核是项目，Week 10 结束一切结束。（"我也讨厌考试。"）
- **为什么需要过程**：有逻辑、知道下一步是什么、可规划、可预测、保证质量与可维护性（不会日后问"这段代码为什么在这"）——就像盖房子要先有图纸。
- **瀑布模型**（线性、结构化，做完第一步才能开始第二步）六阶段，用"**timetable management app**"和"**盖房子**"作比喻：
  1. **Requirements gathering / engineering**：客户说"做一个课表管理软件"，你要追问：什么意思？要什么功能？用户是谁？——写代码前先弄清需求。
  2. **System design**：房子一层还是有楼梯？几间卧室、有没有厨房厕所？——整体架构设计（三卧两卫一厨一洗衣房，各在哪里）。
  3. **Implementation**：把各个模块（洗衣房、厨房…）真正建出来/写出来。
  4. **Testing**：房子安全吗、符合客户要求吗、厕所不堵吗——检查一切正常。
  5. **Deployment**：房子要有人住——把代码交付给用户，让它不只躺在自己笔记本上。
  6. **Maintenance**：厕所偶尔不通请修一下、请加个新功能——修 bug、加功能。
- **Agile**（听过的举手：一半一半）：更灵活，不要求上一阶段完美才开始下一阶段；**周转更快**，更看重**可工作的软件**而非文档。原因：科技变化太快，卡在需求阶段别人就先做了；用户需求会变；**需求永远不可能完美**，实现/设计/测试时总会发现最初需求不对。因此可以回头、多迭代。Agile 更多是**人的心态（mindset）**而非方法论——后几周细讲。
- Agile 强调灵活、**协作**（不仅团队内，还有客户等利益相关方——持续汇报进度、要反馈；以及领域专家，例如做临床软件要有临床专家参与，涉及隐私和特殊要求）、**持续改进**；把软件开发视为持续学习与改进的过程。项目里会实践所有阶段。
- **Q：能多讲讲现代方法吗？** ——瀑布要"done then done"（需求完美了才设计）；Agile 可以先有 **MVP**——不完美但能跑，拿给客户/用户看"感觉如何"，再持续改进；测试、维护同理。迭代而非线性，永远没有"完全做完"，不追求大量文档。

### 01:10–01:34 Git 演示（单机）

- 为什么学 Git：追踪一切、管理项目、**并发编程**（多人同时在同一代码库工作）。
- 两种使用方式：**终端**命令行；**GUI**（GitLab/GitHub/Bitbucket）——本质相同。今天两种都用。
- **在 GitLab 建项目**：`gitlab.cse.unsw.edu.au` → 右上角 "+" → Create blank project → 命名（示例 `welcome9820`）→ 选择位置（放在自己 zID 下）→ 可见性：**Private**（需授权才能看/改）或 **Internal**（任何登录用户可见；讲师选 internal 方便大家看）。
- **本地获取**：平时不在浏览器写代码，用 VS Code 等编辑器 → 需要 **`git clone`**（把 GitLab 上的项目复制到自己电脑）：在 GitLab 复制 URL → 终端 `cd` 到目标目录 → `git clone <url>` → 输入 passphrase（需先按 lab-git 设置好密钥）→ 得到含 `README.md` 的目录。
- 类比：GitLab 像 Google Cloud 上的一个文档，但它在**远端服务器**；本地要用编辑器工作，所以 clone 一份。
- 本地新建 `git.md`（markdown：不是可运行代码，只是带格式的文本）→ 刷新 GitLab **看不到**——改动只在本地，**还没同步**。
- **四个区域**（课件图）：**Working directory**（你的机器，改动只在本地，不影响用户和队友）→ **Staging area** → **Local repo** → **Remote repo**（GitLab，团队所有人看到同一份）。
- **为什么要分区**（演示）：同时改了不相关的东西——`git.md`（还没学完）和 `week1.md`（本周事项：practice git、kickstart project、form groups）。只想先推 week1：**`git add week1.md`** → 只有它进入 staging；此时远端**仍看不到**。又加了同主题的 `kickstart.md`（放 Python 代码熟悉环境）→ `git add kickstart.md`。两者是同一主题，"打包拍张照"：**`git commit -m "things to do about week 1"`** → 从 staging 进入 local repo，必须写 commit message，一周/一年/五年后还知道自己做了什么。**`git push`**（输入 passphrase）→ 刷新 GitLab，两个文件出现，共享同一条 commit。
- **Q：为什么需要 `git add`？** ——学生：Git 要知道你想把哪些文件打进包里。讲师：没有 staging 就只能把 `git.md`、`week1.md`、`kickstart.md` 这些**不相关**的改动一起提交，历史很乱，别人和未来的你都不知道目的。commit 就是项目**历史**——在 GitLab 的 Commits 页可以看到 initial commit 和 "things to do about week 1"（两个改动文件、具体差异），历史清晰。
- **Q：不小心 add 了不该加的怎么办？** ——留作课后作业自己查（如何 unstage）。
- 回顾流程：GitLab 新建 → clone 到本地 → 本地修改 → add → commit → push。
- **`git status`**：显示当前分支（`On branch main`，稍后解释）、**untracked** 文件（`git.md` 仍在工作目录，从未 add，Git 尚未追踪）、staging 里没有东西。
- 把 `git.md` 也 add / commit（"initial git.md"）/ push。

### 01:34–01:50 多台机器与 merge conflict

- 场景：有时在家用笔记本，有时用学校电脑。演示用 **TigerVNC** 远程控制 CSE 机器当"第二台电脑"（复制 URL 时折腾了一会儿）。在另一台机器 `git clone` → `code` 打开 VS Code → 文件都在（因为 clone 了）。
- 在学校机器上改 `git.md`（加 `git add / commit / push`），回家前要做什么？——学生复习：`git add git.md` → `git commit -m "add git document"`（讲师：commit message 要**有意义**，不要 "fix"、"add new feature"、"random"）→ `git push`。
- 回家打开本地项目却**只有旧内容**——改动在远端；要用 **`git pull`** 把远端拉到本地（"魔法"演示）。**回家/换机器后、动手改之前第一件事就是 `git pull`。**
- 在家再改（加 pull 和 status 到 `git.md`）→ add → commit "add pull and status to git.md" → push。
- 第二天在学校**忘了 pull**，直接改（"silly me forgot pull"，还删了些内容）→ add → commit "silly work" → **push 被拒绝**：`Updates were rejected because the remote contains work that you do not have locally… use pull before pushing again`。Git 很贴心，照提示 **`git pull`** → Git 把远端改动和本地改动**都保留**放在文件里（它不知道该留哪个），由你删掉不要的（删掉 "silly me"）→ 保存 → `git status` → add → commit "fix silly me conflict" → 再 pull 确认 → push。问题解决。这叫 **merge conflict**（代码之间的冲突，不是人之间的）。
- 线上音频短暂中断，修复。
- **Q：只改同一文件才冲突吗？新增不同文件呢？** ——新增不同文件没问题，Git 会自动合并；只有它解决不了的冲突才需要你处理。lab-git 里有练习。

### 01:50–02:04 团队协作：分支与 merge request

- Git 真正的价值在**多人协作**。**Branching** 一开始会困惑，很正常，10 分钟没懂没关系——软件工程靠**练习**，lab 里动手才会懂。
- **Git 树模型**：目前工作的分支叫 **main**（有的项目叫 master，同义）——最重要的分支，**所有能工作的代码放这里，绝不放坏代码**。要加新功能/改代码时，代码暂时不完美很正常，但不能打扰 main → 从 main 某个 commit **checkout 到新分支**，在分支上开发；测试通过、功能就绪后 **merge 回 main**。
- 演示：先 `git pull`（Git 自动合并了之前的改动；只有真正冲突时才让你决定）→ `git status` 显示在 main → **`git checkout -b project-info`**（创建并切换到新分支；分支名要像 commit message 一样有意义）→ 新分支拥有 main 的全部文件 → 新建 `project.md`（"our project is about task tracker"），改动只在该分支。
- `git checkout main` 切回 main —— 结果 `project.md` 仍显示（讲师："VS Code 干的，我讨厌你"）。原因：该文件还是 **untracked**，从未 add 到任何分支，所以切换分支时它跟着走；讲师现场未确认，留作大家本周 lab 探索的题目。
- 功能就绪后把分支合并进 main，方式是**同伴评审（peer review）**——任何合入 main 的代码都要被复查。
- 在 `project-info` 分支：`git add project.md` → `git commit -m "add new project.md"` → `git push` **报错**：`The current branch project-info has no upstream branch`——远端只有 main，没有该分支；按提示 **`git push --set-upstream origin project-info`** → GitLab 上出现第二个分支，并提示 **Create merge request**。
- **Merge request**（在 GitLab GUI 完成）：写标题（"create new project.md as the new project feature"）和描述（加了什么文件、删了什么、其他改动）——MR 比 commit message **更重要**，它是更大的构建块（一个功能/一个 bug 修复，可含多个 commit）；**指定组员为 reviewer**；创建。Reviewer 的职责是检查功能/修复是否就绪、合并是否安全并给反馈（可在 MR 里评论互动）；但**由你自己点 merge**——对自己的代码负责。合并后 main 上出现 `project.md`。
- 结束（超时 4 分钟）："用 lab 练习、练习、练习——merge conflict、branching 全都练。问题发论坛。"

2. **考核**：无考试；唯一作业 = 小组项目 **Task Tracker**，3 个 sprint（Week 4 Mon / Week 7 Mon / Week 10 Fri），每 sprint 有组分 + 个人分和 tutor 反馈；Sprint 1 最易、3 最难；**人人必须写代码**。
3. **分组**：Week 1 lab，随机、4–5 人、不落单女生；有顾虑尽早找 tutor。每周一 newsletter。
4. **AI 使用**：可用于学习/研究，但必须**声明**（哪部分、怎么用、为什么）且能**解释自己的决定**；check-in 时 tutor 会提问。
5. **软件过程六阶段**：Requirements → Design → Implementation → Testing → Deployment → Maintenance（瀑布：线性、上一步完成才下一步；房子比喻）。
6. **Agile 高层**：灵活、协作（含客户与领域专家）、持续改进；MVP 先跑起来再迭代；需求永远不完美；是心态而非方法论。
7. **为什么 Git**：追踪谁改了什么、回退版本、多人并发协作；GitLab/GitHub/Bitbucket 本质都是 Git；分布式。
8. **四个区域**：Working directory → (`git add`) Staging → (`git commit -m`) Local repo → (`git push`) Remote；`git pull` 反向；`git status` 查看状态。Staging 的意义：把**相关改动打包成一个有意义的 commit**，历史清晰。
9. **Commit message / 分支名要有意义**（不要 "fix"、"random"）。
10. **换机器先 `git pull`**；忘了 pull 导致 push 被拒 → pull → 手动解决 **merge conflict** → add/commit/push。Git 能自动合并的就自动合并。
11. **分支**：main 永远只放能工作的代码；`git checkout -b <name>` 开分支开发；第一次 push 用 `--set-upstream origin <name>`。
12. **Merge request**：在 GitLab 建 MR、写清标题与描述、指定组员 review；reviewer 检查并反馈，**作者自己合并**、对代码负责。
13. **练习**：lab-git 不计分但极重要——"practice, practice, practice"。
