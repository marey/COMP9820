### 架构 vs 设计 vs 模式 vs 实现

- **架构** = 应用的最大蓝图 / 路线图，像盖楼先有建筑结构。它描述系统的主要部分（边界）及其关系，是最高层的抽象，可以理解为"方框和线"。
- 核心关键词是 **抽象层级** 和 **推理过程**：做架构和设计是在做决定，决定影响应用的未来——怎么演进、多容易测试和维护。
- **设计**：从架构往下"放大"——有哪些职责、模块、接口、依赖。实现一个用户故事：先列职责 / 功能，再分组成模块，有的需要接口供别的模块调用。
- **设计模式**：反复出现的设计问题的可复用解法。例子：**安全登录 / 认证**几乎每个应用都有、思路都一样，不必重新发明轮子。
- **实现**：函数、类、数据结构、代码、测试用例。
- **架构和设计的核心是"决策"，不只是图。** 为什么这样拆、为什么这样连，才是重点。
- **早期决策会跟很久。** 大公司常在五年后发现当初架构撑不住。**Facebook 的信息流**（无限下滑加载）到了一个点原有架构无法扩展，不得不从根本上改架构。所以要做取舍、给出理由、想清楚再大量写代码。
- **自顶向下**：从代码开始很难看到大图；从"前端、后端、后端再拆子组件"这样的大块开始更容易。架构和设计的思考应在需求之后立即开始，而不是写了一堆类之后再回头组织。

### 工程师思考设计的 6 个问题

- 设计看起来简单（几个框几条线），难在"怎么拆怎么分"的决定。这 6 个问题是初学者指引。
- **解决什么问题**：普通的"登录 / 看数据 / 浏览 / 购买"应用，和 **事件驱动** 应用（事件触发才反应）是两类不同的问题。
- **什么会变**：敏捷拥抱变化。数据库会增长？业务规则会变多？以后会加服务？知道哪些会变，就从一开始为变化设计。
- **什么放一起 / 什么分开**：HTML 结构和样式放一个文件，改一个样式就要动整个文件；分开后更容易改、更容易理解。
- **怎么测试**：用户故事定义得小就是为了可测、可衡量进度。
- **什么可能失败**：会拖垮整个应用的东西是高风险组件，要有策略单独处理。

### 架构图：用来沟通，不等于架构

- **图不是架构**。架构是一组设计决策（为什么拆、为什么合、为什么单向通信）。
- 图的价值是让沟通更容易：只看源码很难理解全貌。C4 四层：语境（谁在用、从哪用）、容器（应用和数据存储）、组件（应用内部职责）、流程（请求怎么流转）。
- 工具是为了效率，**但别陷进工具里把图做得完美**——决策才重要。
- **最常画、通常也够用的是语境图 + 容器图**；对学生 Web 项目一张语境图 + 一张容器图就能起步。

### 从用户故事到职责

- 用户故事已经把需求拆成可作为小单元实现的功能。用户故事 → **职责**（系统必须做什么，通常不止一件事、不止一个函数）→ **组件**（职责住在哪）→ **接口**（组件之间怎么通信）→ **质量检查**（仍然安全、性能、可测、可改）。

### 课堂活动：什么指导敏捷团队做架构和设计？

- 讲师先问"你们团队采用 Scrum，什么在指导你们做架构和设计？"——无人回答；提示"我们讲敏捷时最先讲的是什么"，放出第二问"敏捷方法论怎么对待架构和设计"。答案：敏捷没有唯一定义，有的是 **价值观和原则**，其中有些明确谈到设计和架构。
- **回顾 4 条价值观时的互动**：
  - 学生答 **"简单"** → 讲师：对，目标是可工作的软件，哪怕功能很少；不要从庞大复杂的架构开始，而是从一小组用户故事开始。
  - 讲师问 **"谁来做设计和架构？项目经理？Team lead？"** → 学生答 **软件架构师** → 讲师：架构师或资深工程师可以 **牵头**，但 **不会一个人做**——"个体与互动"要求多人一起，包括 **带来业务领域知识的客户**。例子：客户说"我们的应用完全靠事件——股票交易，一有事件就要买卖"，不早期、定期和客户协作就会做错架构决策（后面讲事件驱动）。
  - **响应变化**：不会一开始就花几周几个月做"完美"设计；从一个起点开始演进、迭代、增量，因为一次做不对。
  - **面试 / 带团队时被问到怎么看设计和架构，应引用 4 条价值观和 12 条原则。**
- **回顾 12 原则时的互动**：讲师问哪些原则明确谈到设计和架构？学生答 **第 9 条**（持续关注技术卓越和好设计能增强敏捷性）；第 10 条简单也相关。讲师再问还有没有——无人答出，讲师指出 **第 11 条**：最好的架构、需求和设计来自 **自组织团队**（一起做决定、不是一个人领导；即使有架构师，让其他人参与也能带来重要视角）。上周讲需求时也提过"和业务人员一起工作"同样适用于设计。
- 结论：**随时回到价值观和原则来推导自己在设计和架构上的思考。**

### 敏捷价值观 → 设计决策；本课程的脉络

- 可工作的软件 → 设计"够用"的结构交付可用增量；响应变化 → 职责和依赖分开，"只改登录，不用改整个认证流程"；技术卓越 → 测试、重构、清晰接口；客户协作 → 早拿反馈、早定设计优先级。
- **课程脉络**（讲师坦言顺序不好安排——先学 Git / GitLab？先 CI/CD？先需求？先设计？）：先学敏捷计划和 Scrum（用户故事、验收标准、Sprint 计划、事件工件）→ 把用户故事翻译成组件、职责、边界 → 从一开始内建质量。
- **测试只是 DevOps 的一个组成部分**，DevOps 下有持续集成、持续交付；CI/CD 流水线保证每次改动 / 重构都有质量保障。

### 敏捷设计是迭代增量的；用户故事例子

- 用户需求 → 小设计 → **可工作的切片** → 反馈 → 演进的设计。**目标是尽早拿到反馈**：不做出来、不给看，就拿不到反馈，也就没法调整设计。设计不是"给开发团队一堆设计文档"，而是让改动更快、更便宜、更干净的一组决策。
- 例子"作为注册用户，我想提交一个请求并跟踪状态"：**不是一个函数**——要有表单；**提交到后端之前先校验**；校验通过后应用业务规则（这个用户是否允许提交、是否有权访问）；存储和读取状态。一个故事的职责分布在前端、后端（后端又多个组件），中间通过有格式 / 契约的 HTTP 请求通信。

### 基本 Web 架构与课堂活动：前后端职责分类

- 用户 → 浏览器（前端）→ HTTP / API → 后端（业务逻辑）→ 数据。用户只做"一件事"，但职责清楚地分在不同组件、有清楚的流程。请求 / 响应大多由浏览器处理，你不用亲自管，但要理解它。
- **课堂活动**：讲师问两组职责是混的还是刚好一组前端一组后端？学生看出 **右边一列是前端**，左边全是后端。
- **这就是实现用户故事时要做的决策。把后端职责做到前端就违反了设计原则，会造成大问题。**
- **校验要做两次，理由不同**：
  - **前端校验是为了性能 / 体验**：不想发到后端再等响应——走网络要时间；无效邮箱 / 密码能在前端查就在前端查。
  - **后端校验是为了安全，是后端的责任**：用户或 **黑客** 可以发"看起来校验过"但能搞坏代码的东西、注入可疑代码、绕过前端校验。
- **API 是契约，不只是一个 URL**：端点（功能在服务器哪里）、方法、输入、响应、错误规则。练习的目的是把正确职责放进正确组件、把边界设清楚。

### 设计原则（休息前）

- 好结构的意义：我们 **预期变化**，架构和设计会演进、不是一次完成；边做边不断做决定、修正决定。
- 做好决策靠经验：初级 → 高级 → 架构师，架构师经历过从代码到完整架构的全过程，知道早期决策怎么影响后来。
- **关于 AI 的题外话**：公司用 AI agent 写代码，会议上都在讨论该教什么。常听到"初级工程师不再需要，需要更资深的人"。**资深 = 理解设计和架构决策的人**——能判断 AI 写的代码好不好、让它按某种方式改，因为不能完全信任 agent。有人说"一切看起来很好、能跑"，然后规模上去就挂了。所以要有人引导 AI agent，这个人必须懂设计原则、也懂好代码。
- 8 条原则的讲解要点：
  - **关注点分离**：前端负责某些事、后端负责某些事，各自对应代码里的函数，后端内部还可再分。
  - **封装**：例子是 **类**——数据只通过类的方法操作，外界只通过方法和它对话。
  - **高内聚**：相关行为放一起，为了 **把变化局部化**；散在不同组件时改一个行为要改多处、每处都要重测，很贵。
  - **低耦合**：有人叫"解耦"。高耦合 = 组件彼此严重依赖、做一件事要调很多别的组件。**耦合不可能避免，目标是最小化。**
  - **简单依赖**：A 调 B 调 C 的传递依赖要少，依赖要清楚、可见、直接。
  - **为变化设计**：架构师会问"什么最常变"，把它放进一个组件 / 模块。
  - **YAGNI** 和 **KISS（Keep it simple, stupid）**：一个东西只做一件小事。开发者常说"以后可能用得上"往一个类 / 函数里塞职责，后来根本用不上——更大、更难维护、更难测。
  - **持续重构**：边做边改进设计；一个故事穿过多层（垂直切片），能早拿反馈、早测试、早发现问题。
- **关注点分离例子**（记开销穿过 5 层）：前端只管收集数据和反馈；业务逻辑只校验开销规则；**业务逻辑不直接调数据库**，要通过专门的数据访问组件。改数据库访问只改那一部分；加业务规则直接加、调用就行。
- **封装与依赖方向例子**（Expense service 用数据库适配器和通知适配器）：不是为了造很多层，而是把职责封装在服务里，数据和通知的细节放在适配器。**测试时可以把通知适配器换成 mock**，没有真通知服务也能测；数据库同理。
- **对你们项目的直接建议**：你们刚开始，**不用太操心后端**——可以先做前端，**后端用一个"假服务"mock 掉，比如一个文件：读文件返回一个字符串**。决策可以简化，但设计上这段代码 **不在业务逻辑里，而在单独的适配器 / 组件里**，换数据库时不需要改 expense service。
- 职责缠在一起（一个模块画表单、验权限、算费用、写库、发邮件）很难改；分开后改适配器不用把所有东西重测。
- **内聚与耦合**：目标是高内聚 + 低耦合（开销模块只管开销三件事，通知模块只管通知），不要 UtilityManager 式的万能类。始终问："改这个职责，要看懂并修改多少不相干的地方？"
- **课堂活动：两种架构选哪个？** 学生答 **选 2（一个可部署的 Web 应用），理由是"可工作的软件"**。讲师：对——一个应用，增量往里加，模块清楚、API 边界定义好，以后有证据再抽服务。架构 1（12 个服务、3 个消息队列、自研插件平台、全球多区域复制）是在 **猜测** 未来需要，没有证据就没有价值。**设计 Sprint 要简单，用 YAGNI。** 和用户故事 / Scrum 一样：不预测未来，只为确定能在一个增量里交付价值的东西设计；用户真的提出要加服务时再加。

### Web 应用的架构（休息后）

- 浏览器上一次点击背后是一条用户看不见的 **职责链**，工程师要设计这条链。
- **最简单有用的 Web 架构**：浏览器 / 客户端 ⇄ HTTP ⇄ Web / API 服务器 → 数据库；服务器 → API → 外部服务。
  - **浏览器替你做了很多**（准备请求 / 响应等），你只写页面、样式、JavaScript（触发动作、校验输入、处理交互和 UI 状态）。学 Web 开发会了解 HTTP 的各种方法。
  - 服务器定义业务规则、认证、授权，有若干端点（URL + 参数）对应不同职责；服务器和浏览器分开、通过 HTTP 通信。
  - **数据库和客户端的直接访问隔开**。外部服务（扣款、真实支付系统、地图）通过 API 调用并配置，结果存回数据库。
  - 要做快速响应的界面，要理解浏览器怎么工作。
- **前端**：展示和交互，**不要把业务规则放在浏览器里**；前端校验是即时反馈，**服务器仍然再校验**——黑客知道怎么绕过，可能破坏数据库或做未授权的事。
- **后端**：按 HTTP 收请求回结构化响应；校验；**认证**（确认用户是谁）；**授权**（能做什么——例子：**只能看自己所在群组的开销**）；业务逻辑算分账、余额；通过数据访问层读写；集成外部服务；**可观测性 = 每个组件都记日志**，出问题才能定位是读库还是写库出错；拆分太多时这件事会变复杂。
- **API 契约**：GET 取、POST 存，有结构、状态码、校验规则。**好契约降低耦合，因为代码在契约里不在两边**；但协调仍然存在——**所以叫低耦合不叫解耦**。

### 架构模式一：分层架构

- 分层是 **关注点分离原则的落地**——前面讲的原则开始"活"在常见模式里。展示 / API 在前端；**应用服务层** 可能直接回答一些请求，也可能要经过领域规则或数据访问。
- **展示层不能直接访问数据访问层或数据库，必须一层层经过**：有的请求在应用服务层就返回；有的要经过业务逻辑检查规则（可能在访问数据库之前就返回）再到数据库。
- 好处：加业务规则、改应用服务、改数据库访问方法互不影响；加新数据源只在数据访问层加方法。
- **安全**：黑客不能直接碰数据库，必须经过所有认证 / 授权检查。
- **部署可以不同**：各层各在一台服务器（跨网络 HTTP / API 调用），或全在一台服务器但作为独立组件——逻辑分开，物理可合可分。
- **一个故事端到端**（记开销：表单 → POST /expenses → recordExpense → 校验分账 → 保存 → 数据库行）：**每层可以单独测**（validate split、record expense、save expense 各写测试），不必把所有东西放一起测；**可以用假的替换真的**——不用真数据库，用一个文件读写来测服务层。不同类型的测试 **下周讲**，重点是保证组件集成起来、请求能一路走通。

### 架构模式二：MVC

- 讲师问 **有没有人用过 MVC**——没有人。它很常见，很多课程和 Web 开发都教，同样基于关注点分离。
- **视图**：显示、接收输入（点"加入购物车"、搜索）交给控制器，也显示返回的结果。**控制器**：收到请求 X 知道该调哪个模型；**控制器不直接访问数据库**。**模型**：数据和领域行为（"把用户要的 X 都取出来"）。每种请求 / URL 对应一个控制器，三者之间有映射。
- **Web 版（讲师以前用 Node.js + Express.js 教的例子）**：浏览器 HTTP 请求 → **路由**（每种请求映射到一个控制器）→ 控制器 ⇄ 模型 ⇄ 数据库（比如 MySQL，可在单独服务器）→ 控制器选视图模板生成响应。路由 / 控制器 / 视图 / 模型在应用服务器；也可以全放一台服务器，由你决定，但要想到跨网络调用和扩展问题。
- 8 步流程（请求进 → 路由 → 控制器 → 模型 → 数据库 → 模型 → 控制器 → 视图 → 响应）就是你实现时在做的事："收到请求 X 给控制器 X，请求 Y 给控制器 Y"，控制器根据请求决定调不调模型。
- **目录结构**：controllers / models / routes / views 各一个文件夹，图片、CSS 各有位置——**每个文件夹是一个模块，模块下是源码文件**，这就是把架构组件映射到代码结构。
- **现代 Web 应用的 MVC**：Python 里叫 **MTV（Model–Template–View）**；客户端逻辑、事件、状态、API 调用大多在浏览器端；服务端专注路由到逻辑、再到模型和数据库。**Django 这样的框架开箱给你这套结构**——很多语言 / 框架采用了这些被广泛认可的模式，你只需知道怎么组织、怎么调用。

### 架构模式三：微服务（事件驱动一页课上没讲）

- 微服务 = **每一个小功能做成一个服务**（认证用户是一个服务；用户服务、开销服务各有逻辑）。**数据也拆成"微数据库"**：用户服务只有用户数据，**不需要访问开销库**。组合逻辑（"群组里谁付了什么"）要调多个服务拼出来。每个服务有自己的 API，**API 网关** 收到请求知道该调哪个服务——所以叫网关。
- **好处**：**只扩展瓶颈组件**——假设用户服务负载不大，但开销服务 **每秒上千请求** 成了瓶颈，就只把它部署到多台服务器分流，而不是扩展整个应用；**故障隔离**（一个挂了不影响其他）；**安全**（攻破一个拿不到其他库和服务）；CI/CD 看起来更容易（小组件独立运行）。
- **代价**：分布在不同服务器 **追踪很难**；**网络故障和延迟**；**数据一致性**。**没有理想方案、没有银弹，只有决策和取舍——这就是"架构 = 设计决策"。**
- **别因为微服务"听起来可扩展"就选它**：有公司收益明显，但要看应用、领域、问题；**延迟敏感的应用** 不能容忍大量网络调用。
- PDF 附录里的 **事件驱动 / 无服务器** 一页，讲师在课堂活动时说"后面会讲"，但最终跳过了。

### 架构取舍与非功能属性

- 5 个取舍问题里，**团队规模** 很重要：团队大、组件拆太多（如微服务），运维开销巨大。部署：每次构建都要部署到基础设施，不同组件部署到不同服务器会拖慢交付、让追踪更复杂。
- **性能 vs 安全**：所有东西含数据库放一台服务器 → 不用跨网络、性能好；但攻破这台就拿到一切。分开放是另一回事。**永远是取舍。**
- **可扩展性** 例子：100 个用户时一个请求约 600 毫秒，**1,000 或 10,000 个用户时还是吗？** 延迟可能增加。
- **可靠性**：依赖挂了要有 **failover**——组件自动部署到另一台服务器启动，用户完全感觉不到。
- 其他：可维护性；**可理解性**（队友和自己能不能看懂并改——全在一个大文件、到处依赖就很难）；**可测试性**（职责拆好边界清楚才能定义好测试）；**模块化**（MVC 按文件夹模块化）；**可扩展性 / extensibility**（加服务别的组件不用改）；**可部署性**。
- 设计时要想这些，不是"能跑、够快"就行；代码越大这些越突出。

### Scrum 里的设计：垂直切片与涌现式架构

- 每个 Sprint 交付一个小的端到端能力，而不是不连通的技术层。
- **课堂活动**：Sprint 1 做数据库、Sprint 2 后端、Sprint 3 前端？还是故事 A、B、C 各自跨所有组件？**学生：显然选切片。**
- **要避免的情况 capstone 里也有**："我们做了全部后端，另一拨人做全部前端，最后再集成"——**大爆炸集成（big bang integration）**：最后把所有东西放一起再找哪里出了问题。
- 正确做法：故事 A 做表单 UI、调 API、检查规则、检查数据库、测试、和其他代码集成；B、C、D 同样，不管同一 Sprint 还是不同 Sprint。
- 好处：**早拿反馈**、边做边测、细化设计和架构；有 **明确证据** 知道哪里要改；要测大流量也能早测早改。**早期的改动让团队日子好过。**
- **涌现 ≠ 偶然**：每次做故事都要有决策；现在设计够用不必完美，从增量和反馈学习，下个 Sprint 改进。
- **"虽然我们不要求你们展示设计和架构，但希望这种思维指导你们的决策"**：怎么拆职责、组件放哪、在哪实现。**Sprint 结束 ≠ 开发结束**，有更多反馈可以继续改。
- "Applying the ideas to your project"和两页要点讲师没有逐条讲，留给大家自己看。

### Sprint 1 评估（课末）

- Sprint 1 评估已发布，聚焦第 1、2 周（主要第 2 周）的内容。**总共 30%**。
- **Demo（10%）**：在自己的 lab 演示——目的是让学生 **开口讲、沟通自己的工作**。10–12 分钟；讲给 **tutor 和其他队** 听，**要想着不同的听众**；**每个成员必须出席并讲一部分**，有特殊情况要 **申请 special consideration 才能拿团队分**；两部分：展示实现的功能 + **展示 Sprint 是怎么跑的**（你们应该按 Scrum 做了，我们要确认做对了）；**提交录像作为证据**；应用先跑起来、GitLab 标签页先开好——**为了效率**。
- **Team Report（15%）**：约 15 页五部分（角色与会议记录、计划、跟踪、速度、回顾）。**Velocity 这部分没有对错，重点是解释和论证**——讲 Scrum 时就说过很多事不是对错而是要说明理由：表明你们按 Scrum 正确做了（Scrum Master 要确保），同时能解释。例子：**承诺 15 个故事点完成 12 个，解释发生了什么**——这是估算，而且是你们第一个 Sprint。**我们要看到理解，而不是盲目走流程。**
- **Peer Evaluation（1%）**：每个成员评价其他成员，目标是 **建设性反馈、不是指责弱点**，帮助别人下个 Sprint 改进。**必须按时交，不允许迟交**，除非有批准的 special consideration 或 ELP。
- **Individual Report（4%）**：团队报告 **一周之后**；谈你的贡献和工作证据；让你持续反思自己在做什么、怎么改进、对团队的贡献——用来评估个人贡献。
- 参考文献是讲师用到的，想看更多可以去读。
- **下周：软件测试**——很大的主题，是 **Sprint 2 和 3 的重要部分**，也是开始 CI/CD 前的桥梁（测试是 CI 的重要组成）。有问题可以下来找讲师。

## 核心要点速览

1. **本周内容定位**：接触概念、指导思考；**Sprint 1 不评估设计与架构（讲师认为 Sprint 2、3 也不会）**，但它是 COMP9900 capstone 的重要考核点。
2. **架构 = 决策，不只是图**；早期决策会跟很久（Facebook 信息流改架构的例子），要做取舍、给理由、想清楚再大量写代码。
3. 四个层级：架构（方框和线）→ 应用设计（职责、模块、接口、依赖）→ 设计模式（如认证的现成套路）→ 实现（函数、类、测试）。**自顶向下**，需求之后立即开始想架构。
4. 6 个设计问题：解决什么问题、什么会变、什么放一起、什么分开、怎么测试、什么可能失败。
5. 架构图是沟通工具，**语境图 + 容器图通常够用**；别陷进画图工具。
6. **敏捷怎么指导设计**：回到 4 条价值观和 12 条原则（**第 9、11 条明确谈设计 / 架构**）；架构师牵头但自组织团队一起决定，客户带来领域知识；面试被问时就引用它们。
7. 一个用户故事 = 多个职责，分布在前端、后端多个组件；**前端校验为了体验，后端校验为了安全，两次都要做**；把后端职责做进前端是违反原则。
8. **API 是契约不是 URL**：端点、方法、输入、响应、错误规则；好契约降低耦合但不消除协调——所以叫低耦合不叫解耦。
9. 8 条设计原则：关注点分离、封装（类）、高内聚（变化局部化）、低耦合（最小化而非消除）、简单依赖（少传递依赖）、为变化设计、YAGNI / KISS、持续重构。
10. **对项目的直接建议**：先做前端，**后端可以先用"假服务"（如读文件返回字符串）mock 掉**，但要放在单独的适配器 / 组件里；课堂活动一致选"一个可部署的 Web 应用"而不是投机式的 12 个服务。
11. 分层架构：展示层不能直接碰数据库，请求一层层往下、响应往上回；安全和可测试性都来自这一点；逻辑分层与物理部署是两回事。
12. MVC：视图 / 控制器 / 模型各司其职，**控制器不碰数据库**；Node.js + Express 的路由 / 控制器 / 模型 / 视图文件夹就是模块；Django 叫 MTV，框架开箱提供模式。
13. 微服务：每个小功能一个服务 + 自己的微数据库，通过 API 网关进入；**只扩展瓶颈组件**、故障隔离、安全隔离；代价是追踪、网络延迟、数据一致性、运维——**没有银弹，别因为"听起来可扩展"就选**。
14. 非功能属性都是取舍：一台服务器快但不安全；100 用户 600 ms 到 10,000 用户还成立吗；failover；可理解、可测、模块化、可扩展、可部署。
15. **垂直切片**：每个故事 UI → API → 规则 → DB → 测试 → CI，每个 Sprint 都能演示、能测；避免"后端组 / 前端组最后大爆炸集成"（capstone 里常见）。
16. 涌现式架构 ≠ 偶然：现在设计够用、从增量学习、下个 Sprint 改进；Sprint 结束 ≠ 开发结束。
17. **Sprint 1 占 30%**：Demo 10%（10–12 分钟、全员到场讲、功能 + 过程、录屏、提前开好应用和 GitLab）；Team Report 15%（约 15 页五部分，**速度部分要解释论证，展示理解而不是走流程**）；Peer Evaluation 1%（建设性、**不接受迟交**）；Individual Report 4%（一周后，自己的贡献与证据）。
18. 下周：软件测试，Sprint 2、3 的重点，CI 的前置。
