# COMP9820 Software Project Management · 每周一句话课程大纲

> 用途：26T3 开学公开课宣传
> 依据：26T1 Week 1–9 讲座整理（讲师 Dr. Yuchao Jiang，UNSW CSE）
> 一句话概括：**不教编程，教你在多人协作时管理代码、管理项目、管理人**——无考试，只有一个 10 周、3 个 Sprint 的小组项目「Task Tracker」。

---

## 十周一览

| 周 | 主题 | 一句话 |
|---|---|---|
| **W1** | SPM 导论 · Git 单人/团队用法 | 为什么"会写代码"离"会交付软件"还很远：认识瀑布与敏捷，用 clone / commit / push / 分支 / Merge Request / peer review 迈出团队协作第一步。 |
| **W2** | 敏捷团队实践 | Agile 不是流程而是哲学（"You cannot *use* Agile, you can only *be* Agile"）：用 Sprint、团队契约、站会、Issue Board、结对编程和冲突处理把一个随机组成的小组变成能干活的团队。 |
| **W3** | 规划与用户故事 · 持续改进与 Retro | 计划不是不要，而是要小块、以客户为中心：从需求工程四步写出带验收标准的用户故事，并用五步 Retro 在心理安全的氛围里让团队每个 Sprint 都变好一点。 |
| **W4** | 软件测试与 TDD · 持续集成 | 反馈不只来自人，也来自代码本身：用 pytest 把测试写成代码，按 Red → Green → Refactor 先写测试再实现，再用 `.gitlab-ci.yml` 让每次 push 自动跑测试——main 永远绿，没绿勾不合并。 |
| **W5** | 管理与指标（覆盖率）· 面向可维护性的设计 | 指标是用来开启对话的，不是记分的（覆盖率一变成 KPI 就有害）；软件必然变化，所以要用 DRY / KISS / YAGNI / 低耦合高内聚这些原则设计代码，并在测试保护下重构。 |
| **W6** | 部署 / DevOps（Deployment Lab） | "在我电脑上能跑"不够：把 Task Tracker 部署到真实环境（Vercel），第一次看到自己的应用真正上线。 |
| **W7** | 持久化 · 软件复杂度 | 重启服务器数据还在，才算真正可用的产品（用 JSON 文件做最简单的持久层）；学会区分本质复杂度与偶然复杂度，用耦合/内聚与圈复杂度找到最该重构的那段代码。 |
| **W8** | 风险管理 | 项目失败大多不是技术原因而是管理原因：识别 → 分析 → 排序 → 缓解，用风险登记表在问题变贵之前把不确定性管起来。 |
| **W9** | 回顾、综合与展望 | 把九周碎片拼成一张图——SPM 就是平衡范围、进度、质量、人和风险；带走三大主题：可追溯性、自动化、心理安全，以及一份能拿去面试的个人作品集。 |
| **W10** | Final Demo | 向"客户"正式演示 Sprint 1–3 的全部成果：讲用户是谁、解决了什么问题、创造了什么价值，而不是逐行讲代码。 |

## 三个 Sprint 与讲座的对应

| Sprint | 周 | 讲座支撑 | 一句话 |
|---|---|---|---|
| Sprint 1 · 基础起飞 | W1–3 | W1 Git · W2 敏捷 · W3 故事/Retro | 组队、立规矩、写故事，每个人都提交自己的第一个 Merge Request。 |
| Sprint 2 · 质量与 CI | W4–6 | W4 TDD/CI · W5 覆盖率/可维护性 · W6 部署 | 从"做出来"到"做得好"：测试先行、CI 必做、覆盖率看缺口、尝试上线。 |
| Sprint 3 · 交付与风险 | W7–10 | W7 持久化/复杂度 · W8 风险 · W9 回顾 | 端到端交付：数据可持久、复杂度可控、风险有预案，最后正式 Demo + 个人 Portfolio。 |

## 贯穿全课的三句话

- **Traceability（可追溯）**：Issue = 工作，Commit = 实现，MR = 集成，任何人都能看到谁在做什么、为什么。
- **Automation（自动化）**：手工做在大代码库上太慢，测试、CI、覆盖率全部交给流水线。
- **Psychological safety（心理安全）**：Retro 里人人敢说话，团队才会真的进步。

**保持回路短：Plan → Build → Test → Deploy → Reflect。**
