# COMP9820 公开课：从“会写代码”到“会交付软件”

> Header topic: Software Project Management
> 课件类型：60 分钟公开课 Markdown 课件
> 贯穿案例：一个由多人共同开发的 Task Tracker
> 核心问题：怎样让一个团队持续、可靠、可验证地交付软件价值？

---

## Slide 1 · 开场：代码能运行，项目就成功了吗？

Sub: 软件项目失败，往往不是因为团队完全不会写代码

### 三个真实问题 · single

#### 问题一：需求真的清楚吗？

- 团队按时完成了全部功能，但用户发现产品没有解决真正的问题。
- 每个人都在忙，却没人能解释为什么要做这些功能。

#### 问题二：多人协作可靠吗？

- 两个人同时修改同一段代码，合并后主分支无法运行。
- 任务散落在聊天记录、口头承诺和个人笔记里。

#### 问题三：质量能被证明吗？

- “在我电脑上能跑”不等于其他人能运行、测试和维护。
- 出现问题后，团队找不到对应的需求、修改记录和负责人。

> **公开课主张：**软件项目管理（Software Project Management, SPM）不是管理者独有的工作，而是每个团队成员共同建立的交付系统。

> 讲师提示：请听众先选一个最熟悉的问题，再追问：“如果只靠更努力地写代码，这个问题会自然消失吗？”

## Slide 2 · 软件既是技术系统，也是社会系统

Sub: 会写代码是起点，能让多人围绕同一目标合作才是项目能力

### 技术系统 · single

#### 我们需要管理什么？ · side-by-side

##### 代码与工具 (qbox)

- 版本、分支与合并
- 自动化测试与持续集成
- 部署、数据与运行环境
- 可维护性与技术风险

##### 人与决策 (qbox alt)

- 用户价值与优先级
- 分工、沟通与冲突
- 反馈、复盘与持续改进
- 责任、证据与共同理解

#### 项目成功的重新定义 (quote)

> 成功不是“完全按照最初计划执行”，而是团队能在变化中持续交付有价值、可验证、可维护的软件。

## Slide 3 · 贯穿案例：Task Tracker 不只是一个小网站

Sub: 用一个简单产品，暴露真实团队协作中的复杂问题

### 用户问题 · single

#### 场景

一个团队用便利贴、群聊和截图管理任务，结果经常出现：

- 任务被遗忘或重复创建；
- 截止日期不一致；
- 不知道任务由谁负责；
- 项目进展只能靠“问一圈”才能确认。

#### 最小产品目标

构建一个 Task Tracker，使用户可以查看、添加、编辑、删除和分配任务。

#### 真正的学习目标 (highlight)

产品本身并不复杂。挑战在于：多人如何把需求、任务、代码、测试、评审、风险和反思连成一个可靠的工作系统。

> 讲师提示：强调“功能简单”是刻意设计。只有把功能复杂度压低，听众才看得清项目管理机制本身。

## Slide 4 · 从瀑布到敏捷：计划不是承诺书

Sub: 计划的价值，是帮助团队学习和调整，而不是假装未来不会变化

### 两种开发观 · single

#### 瀑布模型（Waterfall） · side-by-side

##### 典型流程 (qbox)

需求 → 设计 → 实现 → 测试 → 部署 → 维护

##### 适合的问题 (qbox alt)

边界较稳定、阶段依赖明确、变更成本可以提前控制。

#### 敏捷（Agile）

- 仍然需要计划，但更重视**响应变化**；
- 仍然需要文档，但更重视**可工作的软件**；
- 仍然需要流程，但流程必须服务于**人和价值**；
- 用短迭代尽早展示结果，从反馈中修正方向。

#### 关键澄清 (quote)

> 敏捷不是一套照着打勾的工具清单，而是一种适应性、协作性和持续改进的工作哲学。

## Slide 5 · 三个主题贯穿整个项目

Sub: 可追溯、自动化、心理安全共同决定团队能否稳定交付

### 主题一：可追溯性（Traceability） · single

#### 看得见“为什么”和“怎么做”

需求、Issue、代码提交、合并请求、测试和文档彼此关联。任何人都能沿着记录还原一个决策。

### 主题二：自动化（Automation） · single

#### 让机器执行重复检查

测试、持续集成和覆盖率报告自动反馈质量，让团队不依赖某个“英雄”人工守门。

### 主题三：心理安全（Psychological Safety） · single

#### 让问题尽早暴露

成员敢说“我卡住了”“我犯了错”“这个计划有风险”，团队才能在小问题变成事故前采取行动。

> **三者缺一不可：**只有记录没有信任，记录会变成表演；只有自动化没有判断，指标会变成目标；只有友好没有工程纪律，质量仍无法保证。

## Slide 6 · 项目的心跳：保持反馈回路短

Sub: 每轮都产生一个可展示、可测试、可复盘的增量

### 核心闭环 · single

#### Plan → Build → Test → Deploy → Reflect

1. **计划（Plan）**：确认用户、问题、优先级和完成标准。
2. **构建（Build）**：把小任务变成可审查的代码改动。
3. **测试（Test）**：用自动化反馈验证行为与质量。
4. **交付（Deploy）**：让结果离开开发者电脑，进入真实使用环境。
5. **反思（Reflect）**：根据数据和体验调整下一轮工作方式。

#### 为什么要短？ (alt)

- 错误发现得越晚，返工范围越大；
- 需求理解往往在看到产品后才会变清楚；
- 小改动更容易评审、测试、回滚和解释；
- 团队可以在每轮结束时重新排序，而不是被旧计划绑架。

## Slide 7 · 从“做功能”转向“解决用户问题”

Sub: 用户故事让团队先对价值达成共识，再讨论实现

### 用户故事（User Story） · single

#### 基本格式

> As a **[user role]**, I want **[capability]**, so that **[valuable outcome]**.

#### Task Tracker 示例

> As a busy student, I want to assign an owner to each task, so that the team knows who is responsible.

#### 判断一个故事是否有效

- 描述用户和问题，而不是按钮、数据库表等实现细节；
- 使用客户能理解的语言；
- 足够小，可以在一次短迭代内交付；
- 能说明为什么值得优先做。

#### 反例 (bad)

“添加一个蓝色按钮”和“增加一张 owner 数据表”描述的是解决方案，不是用户价值。

## Slide 8 · 验收标准：把“做完”变成共同语言

Sub: 模糊的完成定义，会在开发、评审和演示时反复制造争议

### 用户验收标准（User Acceptance Criteria, UAC） · single

#### 场景式写法

```gherkin
Given a task has no owner
When a team member assigns Alex to the task
Then the task displays Alex as its owner
```

#### 好的验收标准应该

- 在实现前写下，而不是完成后补写；
- 描述外部可观察行为，不绑定内部实现；
- 同时覆盖主路径、边界情况和错误路径；
- 能自然转化为测试和演示脚本。

#### 课堂练习

请为“删除任务”补一个容易被忽略的边界场景。思考：任务不存在、用户重复点击、数据文件不可写时，系统应该怎样反馈？

<!-- ANSWER -->
示例：Given the task does not exist, When the user requests deletion, Then the system keeps the remaining data unchanged and returns a clear message.
<!-- /ANSWER -->

## Slide 9 · 把工作放进可视化系统，而不是放进记忆

Sub: Issue Board 让优先级、负责人、阻塞和进展对全队可见

### 从故事到可执行任务 · single

#### 一条清晰的工作链

用户故事 → GitLab Issue → 负责人 → 开发分支 → Merge Request → 完成

#### Issue 应包含

- 要解决的问题与验收标准；
- 明确、可检查的完成条件；
- 负责人和优先级；
- 依赖、风险或阻塞信息；
- 与后续合并请求的链接。

#### 拆分原则

- 小到可以独立评审和测试；
- 大到能产生一个有意义的结果；
- 不把“前端、后端、测试”永久分给不同的人，避免知识孤岛；
- 发现任务太大时继续拆分，不假装进度正常。

## Slide 10 · Git 不是备份工具，而是协作协议

Sub: 好的 Git 历史能回答“谁、为什么、改了什么、如何验证”

### 团队工作流 · single

#### 安全的主路径

```text
Issue
  ↓
Feature branch
  ↓
Small, meaningful commits
  ↓
Merge Request + peer review
  ↓
CI passed
  ↓
Author merges into main
```

#### 三条纪律

1. **main 始终可工作**：不直接在主分支试验。
2. **提交表达意图**：一个提交只包含一组相关改动，信息说明“为什么”。
3. **合并前同伴评审（Peer Review）**：评审代码、测试、可读性和对其他模块的影响。

#### 可追溯链接

在 Merge Request 中使用 `Closes #42`，让代码改动与对应 Issue 自动关联。

> 讲师提示：可现场展示一个真实 MR，重点不是界面操作，而是让听众观察 Issue、提交、评审意见和 CI 状态如何组成证据链。

## Slide 11 · 测试驱动开发：先定义行为，再写实现

Sub: 测试驱动开发把“我觉得做完了”变成可重复检查的事实

### 测试驱动开发（Test-Driven Development, TDD） · single

#### Red → Green → Refactor

1. **Red**：先写一个会失败的测试，证明需求尚未实现。
2. **Green**：只写足够让测试通过的最少代码。
3. **Refactor**：在测试保护下改善结构，不改变外部行为。

#### 为什么先写测试？

- 迫使团队先澄清行为与接口；
- 测试成为可以执行的活文档；
- 减少“按现有实现倒推测试”的偏见；
- Git 历史能显示测试先于实现，过程本身可验证。

#### 重要边界 (alt)

全绿只说明“已经写出的测试都通过”，不代表系统没有缺陷。测试质量仍取决于人是否覆盖了真正重要的场景。

## Slide 12 · 持续集成：让每次变更自动接受检查

Sub: 机器负责重复守门，人负责价值判断和设计判断

### 持续集成（Continuous Integration, CI） · single

#### 每次 Push 或 Merge Request 自动执行

```yaml
test:
  image: python:3.11
  script:
    - pip install -r requirements.txt
    - pytest
```

#### CI 解决什么？

- 在合并前发现测试失败和环境不一致；
- 给评审者一个共享、可复现的质量信号；
- 让团队更频繁地集成小改动；
- 降低“在我机器上能跑”的依赖。

#### 团队规则 (highlight)

没有通过流水线（Pipeline）的合并请求，不进入 main。

## Slide 13 · 覆盖率是问题探测器，不是成绩单

Sub: 指标应该帮助团队提问，而不是替团队思考

### 代码覆盖率（Code Coverage） · single

#### 它能告诉我们

- 测试运行时执行了哪些语句或分支；
- 哪些区域完全没有被测试触达；
- 哪些改动需要补充主路径、边界或错误路径测试。

#### 它不能告诉我们

- 断言是否真正验证了正确行为；
- 用户最重要的需求是否被覆盖；
- 测试是否稳定、易懂、有价值；
- 系统是否没有缺陷。

#### 指标失调 (bad)

当“覆盖率必须达到某个数字”变成目标时，团队会生产大量廉价测试来刷数字，反而浪费维护成本。

#### 健康用法 (good)

把报告当作对话起点：“为什么这段没有测试？它是低风险、难测试，还是我们遗漏了重要行为？”

## Slide 14 · 可维护性：真正的速度是安全修改的速度

Sub: 软件会持续变化，代码结构决定团队以后还能不能快速行动

### 重构前的七个问题 · single

1. 同一知识是否只有一个权威来源？——DRY（Don't Repeat Yourself）
2. 方案是否足够简单、清晰胜过聪明？——KISS（Keep It Simple）
3. 是否为了想象中的未来提前设计？——YAGNI（You Aren't Gonna Need It）
4. 当前设计是过度，还是不足？
5. 相关逻辑是否靠近，形成高内聚（High Cohesion）？
6. 无关模块是否分开，保持低耦合（Low Coupling）？
7. 是否遵循团队和生态的标准惯例？

#### 复杂度只是信号

圈复杂度（Cyclomatic Complexity）可以用 `V(G) = e - n + 2` 估算独立执行路径，但它不能替代人的判断。天生复杂的业务规则可以保留，前提是团队能解释、测试和管理它。

#### 安全前提 (alt)

没有可靠测试，不要进行大规模重构；把改动拆成小 Issue 和小 MR，让每一步都可审查、可回滚。

## Slide 15 · 从数据持久化看风险管理

Sub: 风险不是一句“可能出问题”，而是可分析、可负责、可验证的行动对象

### 一个具体风险 · single

#### 风险陈述

> If `tasks.json` becomes invalid, then the application may fail during startup, because the loading path has no recovery mechanism.

#### 四步风险管理

1. **识别（Identify）**：什么事件可能阻碍目标？
2. **分析（Analyse）**：发生概率和影响各有多大，理由是什么？
3. **排序（Prioritise）**：有限资源应先处理哪些风险？
4. **缓解（Mitigate）**：降低概率、降低影响，或准备应急方案。

#### 把计划变成证据

- Owner：谁持续监控；
- Mitigation：异常捕获、校验、原子写入、备份；
- Evidence：对应测试、Issue、MR 或监控结果；
- Status：Open / Mitigated / Accepted / Resolved；
- Last reviewed：最近一次重新评估。

> **关键判断：**风险管理只有在改变团队的决策和行为时才有价值；停留在文档里的风险表没有完成工作。

## Slide 16 · 团队实践：让问题更早、更安全地出现

Sub: 高质量协作不是“大家关系好”，而是有明确且可修正的工作约定

### 团队契约（Teamwork Contract） · single

#### 在项目开始时共同约定

- 沟通渠道和响应预期；
- 分工、评审与合并规则；
- 质量标准和完成定义（Definition of Done）；
- 冲突处理与升级路径；
- 契约本身如何更新并保留历史。

### 站会（Stand-up） · single

#### 三个问题

- 我完成了什么？
- 接下来要做什么？
- 我遇到了什么阻塞，需要谁帮助？

站会不是向管理者汇报，而是帮助团队协调依赖、尽早暴露风险。

### 回顾（Retrospective） · single

#### 不问“谁犯了错”，而问“系统怎样改进”

收集事实 → 发现模式 → 寻找原因 → 选择一两个改进实验 → 指定负责人 → 下一轮检查结果。

## Slide 17 · 冲突处理：先恢复共同理解，再恢复进度

Sub: 沟通不是软技能装饰，而是降低项目风险的工程机制

### 情境讨论 · single

#### 场景

一名成员绕过评审，直接把无法运行的代码合入 main；另一名成员在群里公开指责他“根本不会 Git”。

#### 讨论问题

1. 眼前的技术问题是什么？
2. 流程为什么没有阻止它？
3. 公开指责会给后续协作带来什么风险？
4. 团队今天应该修复什么？下一轮应该改变什么？

<!-- ANSWER -->
- 先恢复 main：回滚或修复，并确认 CI 重新通过。
- 私下、直接、礼貌地确认原因：可能是规则不清、不会操作或误点。
- 把“需要评审 + CI 通过才合并”写入团队契约和仓库保护规则。
- 在回顾中讨论流程缺口，不把个人贴成“问题成员”。
- 若直接沟通无效，再按约定升级给课程导师或项目负责人。
<!-- /ANSWER -->

## Slide 18 · 生成式 AI：速度提高了，责任没有外包

Sub: AI 可以降低产出成本，也可以放大低质量流程

### 可以健康使用 AI 的地方 · single

- 帮助理解错误信息或覆盖率报告；
- 起草测试思路，再由人检查行为是否正确；
- 根据真实 Issue、Commit 和 MR 草拟项目总结；
- 提供重构候选方案，由团队逐处评审。

### 三条责任边界 · single

#### 声明（Disclose）

说明使用了什么工具、用于哪部分、如何使用。

#### 理解（Understand）

不合并任何自己无法解释、修改和维护的生成代码。

#### 验证（Verify）

AI 生成的测试、会议纪要、风险说明和报告都必须与真实项目证据一致。

> **底线：**AI 可以生成内容，但不能替团队决定什么有价值、什么足够安全，也不能替任何人承担结果。

## Slide 19 · 一条完整的可追溯交付链

Sub: 最好的项目证据不是一份长报告，而是一组互相链接的真实工件

### 端到端示例 · single

#### 用户价值

用户故事：团队需要为每个任务指定负责人。

#### 可验证链路

```text
User Story + UAC
        ↓
GitLab Issue #42
        ↓
feature/assign-owner
        ↓
Failing test → implementation → refactor
        ↓
Merge Request “Closes #42”
        ↓
Peer review + CI passed
        ↓
main + demo + README / risk evidence
```

#### 这条链能回答

- 为什么做？——用户故事与优先级；
- 谁负责？——Issue、提交和评审记录；
- 做了什么？——代码差异与提交信息；
- 如何确认？——测试、CI 和验收演示；
- 学到了什么？——回顾、风险状态和后续决策。

## Slide 20 · 综合挑战：如果明天开始一个新项目

Sub: 不要先问“用什么框架”，先设计团队的反馈系统

### 小组任务 · single

#### 请为一个四人团队设计“第一轮工作系统”

你们要开发一个简单的活动报名工具。请共同决定：

1. 一个最小、有价值的用户故事；
2. 两条可测试的验收标准；
3. Issue Board 的三种状态；
4. 分支、评审和合并规则；

## Slide 21 · 一页带走

Sub: 软件项目管理的目标，是让价值交付成为一个可持续的团队能力

### 核心结论 · single

1. **从用户价值出发**：故事和验收标准先于实现细节。
2. **把工作放进系统**：Issue、分支、提交和 MR 形成可追溯链。
3. **让机器守重复的门**：测试、CI 和覆盖率提供快速反馈。
4. **让人做真正的判断**：优先级、设计、风险与取舍不能交给指标。
5. **用心理安全暴露问题**：卡点、错误和风险越早说，修复成本越低。
6. **用回顾改进工作方式**：每轮只选少量可验证的改变。
7. **对 AI 产出负责**：声明、理解、验证，不把责任外包。
