## 一、敏捷价值观与原则（pptx p3–p7）

### p3 引言
- 敏捷不同于瀑布流，是近些年比较火的方式；学校主推敏捷。**[新增]** 但敏捷有局限：除非小组里每个人都很强，否则很难推进。
- **[新增]** 历史脉络：2001 年提出，真正流行是 2010 年之后的创业潮（小团队、快速迭代）；最近几年提得少了。

### p5 原则 1–4
- 原则 1：每个 Sprint 都要有能演示的东西。[pptx 已有]
- 原则 2：**[新增]** 随时改需求，正是创业小公司推崇敏捷的原因——快速推出产品满足瞬息万变的市场。
- 原则 3：Sprint 只有 2–4 周，就是为了比别人更快交付到市场。[pptx 已有]
- 原则 4：**[新增]** 业务方天天和开发一起是"理想"，现实里创业公司往往程序员自己就是业务方，所以能快速迭代；对你们来说业务方 = client + tutor。

### p6 原则 5–8
- 原则 5：**[新增]** 团队里每个人都必须能独当一面，这是敏捷最核心的前提；现实中很多公司因人员构成推不动敏捷。
- 原则 6：**[新增]** 瀑布流/企业管理为规避风险常用邮件沟通；敏捷要面对面，SM 要定时组织站会，不能只发消息。
- 原则 7：**[新增]** 群里有同学问 user story 写多少——不要写太多，小步迭代，重点把流程跑通、软件能跑。
- 原则 8：**[新增]** 不要 996 / 通宵赶工，那会限制程序员的创造性思考。

### p7 原则 9–12
- 原则 9/10：**[新增]** 只顾堆代码不反思质量，最后就是改屎山代码，改不动就不敏捷。
- 原则 11：Sprint 1 有脚手架，Sprint 2 起自己定义需求 [pptx 已有]；**[新增]** 建议 Sprint 2 模仿 Sprint 1 的做法，每人提 1–2 个需求，别加太多，务必跑起来。
- 原则 12：回顾会的来源 [pptx 已有]；每天站会也可以顺便反思。

## 二、敏捷开发模型（p8）
- 迭代 + 增量，每轮加一点有用功能。[pptx 已有]
- **[新增]** 落地经验：
  - 每次改动都要小；一个 task 改动的文件控制在 5 个左右，多了继续拆。
  - 一个 Sprint 大概 20–30 个小功能/小任务。
  - 改动小，SM review 代码时才看得懂你在做什么。

## 三、Scrum 角色（p9–p14）

### p9 Scrum 总览
- Scrum 只规定角色、事件、产物，不规定文档怎么写、怎么测。[pptx 已有]
- **[新增]** 三种角色里 PO 和 SM 最重要，一定要负起责来；开发团队相对次要，把自己那份做好即可。
- **[新增]** 需求"砍一刀"法：拿到需求后先列需求点 / user stories（比如 100 条），砍到 50 条，剩下的放进 **Future Tasks** 记录下来；后面做的过程中发现相关又有意思的再捞回来。尽量不要把需求做大。
- **[新增]** 任务时间估算要留冗余：SM 按自己水平估 2 小时的 task，分配给组员时放到 4 小时（组员水平不一、非全职、会遇到额外困难）。
- **[新增]** 投入量参考：大部分同学一周在这门课上约 20 小时；一个人一次拿 4–5 个很小的 task 比较合适；只修这一门课的可以多接。
- **[新增]** 整个项目大概 3 个 Sprint。

### p10 Scrum 团队
- 每组都要定 PO 和 SM。[pptx 已有]
- **[新增]** PO/SM 也要上课也很忙，所以每个人都要负起责来、多盯 issue 和流程、相互督促——敏捷项目的成败依赖每一个人。

### p11 Product Owner
- 唯一负责 Product Backlog [pptx 已有]；**[新增]** "唯一"往往不够，同学们要帮忙维护。
- **[新增]** Backlog 要列上所有任务：开发、测试、上线部署、CI/CD 都列上，对所有人透明。

### p12 开发团队
- 6 人一组。[pptx 已有]
- **[新增]** 每个人都要参与、尽量接 task；能干的多干，不能干的做别的事。
- **[新增]** 有一个人不干活，整个团队质量大打折扣：他在 backlog 里是占人头的（不管分 10 小时还是 20 小时的任务），他不做就只能别人补。SM 要协调好。

### p13 Scrum Master
- 与 pptx 一致：保证团队按流程走、清障、对外打交道。

### p14 Team A / B（Slido）
- 答案 A：每个人都参与。[pptx 已有]

## 四、Scrum 事件（p15–p24）

### p15 事件总览
- 五种活动都要有记录，主要是 SM 的活。[pptx 已有]
- **[新增]** tutor 可能会问你们每天做了什么；要做 **工作日报和周报（work diary / weekly diary）**，开会一定留记录。
- **[新增]** 站会落地形式：每天线上开（如腾讯会议），每人说两句在做什么、进度，让会议工具生成会议总结；任何项目相关的事都可以在会上说。

### p16 Sprint
- 固定 2 周，大概 3 个 Sprint。[pptx 已有 2 周]
- **[新增]** Sprint 里只放"能用、可发布"的东西，**调研性任务不要写进 Sprint**（放 Future Tasks 或自己的时间）。
- **[新增]** 任务不要写得抽象，尽量细化。
- **[新增]** 压力大时的落地方案："一天一个小 Sprint"——早上开个小会定今天做哪几个任务，晚上讨论是否完成。

### p17 Sprint 计划会
- 产出 = GitLab 里绑定 milestone 的 Issues。[pptx 已有]
- **[新增]** 每个人平时都可以把想法、任务随时记进 Product Backlog，开会时再汇总挑选——光靠开会那点时间不够。
- **[新增]** 会议尽量全员参与；任务拆得足够细，太大改代码太多，review 就读不懂了。

### p18 Team C / D（Slido）
- 答案 D：围着任务板一起讨论、认领任务。[pptx 已有]

### p19 每日站会
- 同一时间（例如早上 9 点），三个问题，不解决问题只暴露问题。[pptx 已有]
- **[新增]** 线上也可以，但每天一定要开——这门课本质是项目管理课，开会必不可少。

### p20 开发 & 评审会
- 做不完是允许的，早点告诉 PO 调整。[pptx 已有]
- **[新增]** 评审会和 tutor 一起做：看哪些能跑、哪些做完；没做完的也要汇报，但要有去向：**挪到下一个 Sprint / 放 Future / 实现太难就废弃**，不是写进 Sprint 就一定要做完。

### p21 Sprint 迭代过程
- 右图（每轮从 Backlog 取一部分）更符合敏捷；**[新增]** 落地时两种经常交叉；第一个敏捷项目很难做好，因为要求每个人同频，一个人掉链子整个项目就难受。

### p22–p24 回顾会
- 与 pptx 一致；**[新增]** 回顾时也可以加任务（发现实现不合理），但别加太多。
- **[新增]** 回顾结果写进 work diary / weekly diary，tutor 看得到，向上汇报也有材料。
- **[新增]** 两个示例模板任选一个，或用自己的方式，每人发言后做总结即可。

## 五、Scrum 产物（p25–p28）

### p26 Product Backlog
- 对应 GitLab Issues。[pptx 已有]
- **[新增]** 虽然理论上由 PO 维护，但这不是真实项目，建议每个人都提交想法，由 PO 统一汇总/审核。
- **[新增]** 本学期只用 GitLab（26T1 用过 Jira）。GitLab 里所有管理都靠 **label**：可以加优先级 label，也可以按阶段（讨论 / 开发 / 测试）打 label，一个 issue 多个 label，按 label 过滤。只做优先级高的。

### p27 Sprint Backlog
- **[新增]** 可以加任务、也可以删，但**不建议删**，改成低优先级即可（例：高并发这种往后放）。
- **[新增]** 实际操作通常只看 Sprint Backlog 里还剩多少任务，燃尽图了解即可。
- **[新增]** 如果有人不负责，SM 需要帮他改板子。

### p28 任务板
- 工具：GitLab / GitHub Issues、Trello。[pptx 已有]
- **[新增]** To Do / In Progress / Done 三列可能不够，可以加状态 label：In Test、In Review、In Deploy 等，最后才是 Done。

## 六、用户故事（p29–p37）

### p30–p32 用户故事与格式
- 本周任务：每条需求都写成 user story，尽量详细、尽量小。
- **[新增]** 可以让 AI 写 user story，AI 很擅长；推荐工具 **Spec Kit**（待确认名称）：把想做的东西告诉它，会自动列出相关 user stories，第二轮可以参考、安装试试。

### p34 INVEST
- **[新增]** 把 INVEST 6 条做成项目目录下的 `INVEST.md` / `guideline.md`，每次用 AI 写需求时让它按这个规则来。

### p35–p36 验收标准
- 用 spec 一下就能让 AI 实现 [关联 Spec Kit]。
- **[新增]** 登录例子：一开始很难想清楚要支持邮箱还是用户名、密码要不要校验——第一版就"什么校验都没有"，输入正确格式的邮箱 + 密码就能登录，先把功能演示跑通，验证等后面再加。
- **[新增]** 验收标准一开始想不清楚很正常，因为依赖团队和客户此时此刻的认知；先做最基本的用户需求，后面迭代加；做完发现整个要调整也没关系，这就是敏捷。

### p37 Tips
- MVP 能跑能用就行，不要一上来做高并发之类不现实的东西。[pptx 已有]

## 七、计划、估算与监控（p38–p51）

### p39 计划与估算
- PO 排优先级，干活的人估算，PO/客户不能改。[pptx 已有]
- **[新增]** PO 列了 100 条，Sprint 里尽量放少，分配时间尽量多。

### p40 故事大小
- **[新增]** 不建议用"理想天"，用小时或故事点；不必整组一起估，每个人估自己被分配的任务。
- **[新增]** 时间账：一周 20 小时（约 2.5 天）投入这门课，实际有效大概 12 小时（10–15）；SM 估 2 小时的任务给 4 小时；一个人大约 5 个 task、两天做完比较合理。分太多完不成没意义，也不符合敏捷。

### p42 T 恤尺码
- **[新增]** 用优先级、用 size、用小时都可以，都是估算；大家觉得某任务太大就讨论拆小；做完一个任务主动找 SM 接新任务，快速推进。

### p43 完整用户故事示例
- 一个 story 对应 4 个 task、4 条验收标准、打 M。[pptx 已有]
- **[新增]** 你们的一个 issue 大概 5–6 个 task，尽量拆得足够细。

### p44–p46 总结 & 跑一个 Sprint
- 计划会对着 GitLab Issues 开，每个故事拆成任务卡贴到板上。
- **[新增]** 任务可以是任何项目相关的事：写代码、设计、调研、文档、会议纪要。**组员摆烂时**，沟通不了就让他做需求调研、文档、会议纪要，一定要利用起来——板子上要体现每个组员做的东西。

### p47–p48 燃尽图 / 速度
- **[新增]** 大多数情况不关心这两个，只关心 backlog 里还有多少任务没完成；每个 Sprint 差不多。

### p49–p51 Jira
- 9900 用 Jira，本课只用 GitLab [pptx 已有]；**[新增]** Jira 现在收费很贵，不再介绍；GitLab Issue Board 是同类功能但说实话有点难用，愿意的话可以自学 Jira。

## 八、Git 协作（p52–p54）
- 每个 issue 尽量开一个分支，分支互不干扰，最后合并主线。[pptx 已有]
- **[新增] git worktree**（结合 AI / vibe coding 开发）：
  - 问题：AI 开发速度快、可并行，但一个工作目录同一时间只能在一个分支上；三个 user story 三个分支，改哪个都要切分支，没法并行。
  - 做法：从 main 用 worktree 拉出三个独立目录，分别对应 user story 1 / 2 / 3，互不影响；让 AI 在三个目录同时开发，哪个先完成就合并回 main，合并后删掉 worktree。
  - 工具：VS Code 支持 worktree；推荐 **Orca**（待确认名称，免费，类似 VS Code、只做 vibe coding，按 user story / issue 自动建 worktree，合并后自动删，支持 Claude 和 Codex）。
  - 能把 AI 并行能力用起来，大幅提高开发效率。

## 九、课后问答（p56）
- **问：Sprint 1 只做分组和分账，不用做登录？** 答：对。这门课叫项目管理，重点是管理流程（user story、回顾会、每人参与、每日/每周记录），开发是次要的；管理没做好，开发再绚丽也没意义。每天有点开发投入即可。
- **问：组员都说没时间，11 周可能只能开两次会，能不能在群里每天说一下昨天/今天/困难？** 答：没办法，敏捷每天都要开会，而且要有记录；可以线上开，每天 15 分钟很多分就拿到了；不交流就没有项目管理，分数不会高。
- **问：会议纪要放哪？** 答：所有会议纪要都放 GitLab，在仓库里建一个目录。
