### 考核
- **没有考试**。讲师是项目式学习的拥护者，"考试不能展示学生的才能"。整个学期作为一个团队做一个项目。
- 权重（按交付物）：Demo 35%、团队报告 45%、个人报告+互评 15%、个人反思 5%。
- **Sprint 时间线**：
  - Sprint 1：第 2–4 周。定义 user stories、规划、实现、管理，第 4 周 lab 内 demo + 团队报告（25%）；个人报告 + 互评第 5 周交（5%）。
  - Sprint 2：第 5–8 周。**第 5 周是准备周**——思考变体、定义 Sprint 2/3 的 user stories；第 6 周 flexi week；实际开发第 7–8 周。第 8 周 demo + 报告（25%），个人第 9 周（5%）。
  - Sprint 3：第 8–10 周。第 10 周最终 demo + 最终报告（30%），个人报告 + 互评 + 反思第 11 周（10%）。
- 团队部分在 sprint 末的 lab 内交，个人部分顺延一周交。
- **个人反思**：对整个项目的回顾。ACS、Engineers Australia 等行业机构都要求工程师能反思学习和实践。
- 考核形式：lab 内现场 demo；与 demo 同周交的技术文档；互评（业界通行做法，帮你从反馈中改进）；个人报告（说明你的贡献，教学组也会通过工具和 mentor 观察核实）；期末反思。

### 生成式 AI 政策
- "大家都说 AI 什么都能做。" 但面试时你要证明**为什么还需要人类**——可以和 AI agent 合作，但要有人来领导它们，这门课就是让你建立这种能力。
- **本课采用 UNSW 六级中的 "Simple Editing Assistance"**：不用 AI 做作业。"我们要你自己做、和团队一起做、体验团队协作。" 用 AI 做事的技能可以课外学，但**在团队环境中用一套实践和工具协作**是 AI 给不了你的技能。
- 具体：不许 AI 生成/补全/审查/格式化/调试代码；不许生成报告文本或用 AI 翻译改写已有文本。
- **会检查 GitLab 提交历史**，"公司也是这么做的"——通过工具看谁做了什么，确认每个人真的在贡献。团队提交内容全员连带负责。

### 学好本课的建议与教学理念
- 学的是软件管理，**时间管理**是关键。别拖到最后一刻，每周持续工作；遵循 Scrum/Agile 会让生活轻松——下周讲角色、如何规划/执行/监控。
- 学生常问"一定要做 stand-up 吗？"——公司确实在做，可能是变体；你把标准实践学好，到公司遇到变体也能适应。
- 参加讲座和 lab，练习并反思，享受学习，"这是在投资你的未来"。
- **教学理念**：involve students to learn, not teach them to remember——所以不设考试；一切以学生为中心；与其它课不同的是整个学期一个团队三个 sprint 用同一套工具和实践，所以每周投入至关重要。

### 软件工程导论
- **为什么讲这些"基础"**：让所有人站在同一起跑线。Capstone 里最大的问题就是"队友不会前端/后端/Git/Docker"，造成大量矛盾。单人做事容易，**六人团队 + Scrum + Jira/GitLab** 时复杂性才浮现，这才是要关注的体验。不必为软件本身过度焦虑——软件质量来自团队协作地遵循流程；一个成员不信 Scrum 价值观就会拖累整队。
- **软件无处不在**：电厂、几十亿用户的通讯 App、红绿灯、航班……上周英国航班因软件问题大面积延误取消。想象你在那个团队里，多复杂，多需要遵循实践和工具。安全只是其中一个顾虑。
- 建桥的工程师有严格流程因为涉及人命；软件也一样（连建筑设计都靠软件，软件错了设计就错）。有人质疑软件工程是否重要，但软件工程师仍是美国等国增长最快的职业之一。
- **什么是软件工程**：词云里最大的是 development，但开发只是一项。写代码前要理解问题、需求、用户，设计健壮的架构。
- **为什么需要软件工程**：安全；满足用户需求、可靠可信，否则没人用；失败影响巨大甚至致命；成本——有些项目做了很多年花很多钱最后没有可用产出；上市时间——现在 AI 领域的抢先竞赛。
- **定义**：工程学科，关注从早期规格到投入使用后维护的全部环节，要按工程学科的方式管理和监控，而不是随意/ad hoc。误区：不只是编程；背后有大量关于需求、测试方法、工具的决策；机器人、IoT 等软硬件结合更复杂。

### 软件开发过程
- 类比做蛋糕：同样的步骤，两个人做出来味道和质量不同。
- 四类活动：**规格**（软件的预期行为）；**设计**（用记号表达实现前的结构）；**实现**；**测试**（类型很多，后面专门一讲）；**演进**——软件可能存活几十年，设计时就要考虑可扩展、可维护，不能做成"刚性"的，否则后期改动极其昂贵，而且很难整体替换。
- 每个阶段都能自成一门课，都有大量工作和文档。**人是关键因素**：工具帮你写需求、测试，但"测什么、为什么测"要人来想。
- 有趣的事实：没人能说软件 100% 可靠，十年后还可能发现新 bug。

### 过程模型：瀑布 vs 敏捷（Slido 互动）
- 过程模型描述阶段和顺序；代表是瀑布和敏捷。
- **Slido 互动 1**（slido.com，code 2804174）："用关键词描述瀑布模型。" 84 票，词云：Sequential、Design、Requirements、linear、testing、step by step、Rigid、Traditional、limited change flexibility…（有人把 slido 码当答案输了，"没关系"）。
- 讲师先借此讲团队协作：同一个观点表达方式不同，甚至理解不同，**团队要先对齐认知**。
- **瀑布**：专门的需求工程团队花数月写 SRS，交给设计团队翻译成 UML 等设计，再交给开发团队——"你可能就是那个拿到一堆设计图被要求实现的人"。每阶段试图做到完美再进入下一阶段，**不处理不确定性**；后期发现问题要反馈回起点，代价巨大——刚性、不灵活。它统治了很长时间，也催生了 Agile。
- **Slido 互动 2**："用关键词描述敏捷模型。" 55 票：Iterative、Flexible、Fast、Cycle、Continuous、Feedback、Adaptive、Team collaboration、Sprints、incremental…"很好，我们在同一页上。"
- **敏捷**：为修复瀑布问题而生，关键词 **iterative and incremental**。需求不必完美，随时间演进；挑一些 user stories 在 1–3 周固定 sprint 内做；开发+集成是最长阶段；结束时评审、向客户/用户收集反馈；通过则发布，否则记录变更在下一迭代调整；下一迭代可能是"上轮修改 + 新功能"。你们的项目就是 3 个 sprint。
- 本课用 Agile 中的 **Scrum**，后续详细讲。

### 版本控制与 Git
- 软件由很多文件组成，团队协作时"谁改了什么、最新版本是哪个、能否回滚"很复杂。类比两人在 Google Docs 上改报告、接受/拒绝修订有多麻烦——代码更甚。
- 版本控制：跟踪变化、谁在何时改了什么、回退、比较。团队里每人负责一个 user story/task（工单系统分配），Git 能追踪谁提交了什么；某次改动引入 bug 可以定位并回滚。"report_final_v2"那种命名是噩梦。
- **Git**：分布式版本控制系统。既可单人用，也可团队用——各自持有分布式副本，共享一个中央仓库。源自 Linux 内核开发。每个开发者本地有完整历史；内部把增改作为对象跟踪、通过快照间的 delta 快速定位；可离线工作，需要时再 push 同步。**第一次 lab 就是 Git 命令动手练习。**
- **协作与分支**（讲师详细解释）：把开发想成一条主线。A 拉分支修 bug X，B 拉分支加功能 Y，各自本地工作，主线始终可运行；完成后各自 merge 回主线进入下一个发布。**merge 前先构建测试，确认不会破坏主线**；出问题就回滚。这样 5、6、10 甚至上百人互不影响。没有 Git 你就得自己解决"如何不互相覆盖、如何回滚"，精力从写代码转移到解决这些问题。"Git 帮你处理，但你要懂得用它让团队高效。"

### 安装、概念、命令、工作流、GitLab、SSH
- 安装（Windows/Mac/Linux）；`git --version` 检查；`git config --global user.name/user.email` 设置身份——"谁做了什么"追踪的基础，加入团队时做一次。
- **概念**：工作目录（正在编辑）→ 暂存区（准备提交但未提交）→ commit（创建快照/新版本）；分支；远程仓库（大家共享）vs 本地。
- **基本工作流**：`git init` 让文件夹成为仓库开始跟踪；checkout 到工作目录 → 编辑 → stage → commit 进仓库。关键是**时刻清楚自己处于哪个阶段**，避免混淆。
- 命令行 vs IDE（VSCode Git 面板、GitLab 扩展）：底层同一套命令，会一种即可。
- 命令：`init / clone / status`；`add / commit -m / log / diff`——**commit message 极其重要**，五六个人都提交却不写说明就没人知道改了什么，写"修了 bug X"或关联 Jira 工单；`branch / switch / merge`（团队分支协作第 2 周讲）；`push / pull / .gitignore / stash`。
- 单人流程：编辑 → add → commit → push 循环。**团队流程**：pull → 建分支 → commit → push → 开 merge request → 评审 → merge。合并前必须评审；有时指定专人审所有代码；审不过会退回修改——"这就是控制"。
- **GitLab**：托管仓库 + 问题跟踪 + merge request + CI/CD（后续讲）。课程会搭好环境。Git 是本机工具，GitLab 是团队共享副本所在的平台。
- **UNSW GitLab**：gitlab.cse.unsw.edu.au，用 **SSO 按钮**（zID/zPass）登录——这样教学组能看到所有团队仓库以便反馈和检查。SSH 设置在 lab 详讲。

### 团队协作
- 团队动力学会出现，**这不是坏事，是正常现象**，要学会应对。软件开发是团队活动，Google 等公司几十人一起开发。
- 好团队：凝聚力、互补的技能和知识、团队精神。"不是你怎么做、我怎么做，而是我们**用同样的实践、同样的工具**这样做。" 成员要被团队成功驱动，考虑他人，理解团队目标。
- 沟通和互动不可或缺；Agile 让团队更灵活（后续讲）。
- **计划总会被打乱**：深层技术难题要拆解合作；技术阻塞要先解决；成员背景和贡献不同，要确保每个人都能贡献并遵循同样实践；考核和真实 deadline 带来的压力要管理。
- **选队友**：允许自选，但要明智——考虑角色、技术、知识，形成有凝聚力、目标一致的团队。Lab 会给活动和指南。冲突往往来自组队时没考虑这些。**性格和技术要平衡，一个团队不要三个领导者**，会打架；一个领导 + 其他人配合更好。
- 沟通是 Agile 的核心，能增强凝聚力、理解和生产力，后续详讲。

### 团队冲突（Slido 互动 3）
- 冲突源于竞争、观点不同、都觉得自己对……它存在是因为无法控制性格、心态、文化、背景，**不是"有什么错了"**。
- **冲突强度曲线**（倒 U）：X 轴强度低→高，Y 轴结果负→正。太少冲突 = 大家沉默、隐藏问题；太多 = 人人争着证明自己对；**适度冲突**能分享讨论、接纳他人观点、提前发现问题——不要为"证明我对"忽视别人的好想法，那只会把问题留到以后；把冲突当建设性手段改进需求和方案。
- **冲突过程**（五阶段）："时间不够，图是自解释的"：前置条件 → 感知/感受 → 处理意图 → 行为 → 正/负结果。理解过程有助于及时说"这里有冲突，我们来处理"。
- **冲突类型**：目标型、管理型、人际型。**来源排名**：两组学者的研究中，进度冲突都排第一；管理程序、技术观点、人际冲突也都靠前。
- **Blake & Mouton 模型**：X 轴合作性（满足他人关切），Y 轴坚持性（满足自己关切）→ 竞争、协作、妥协、回避、迁就。
- **Slido 互动 3**：把 5 段描述与 5 种方式配对并排序。28 票结果：Accommodating、Collaborating、Avoiding、Competing、Compromising——与参考答案（迁就/回避/协作/竞争/妥协）基本一致。
- **结语**：这是老模型但至今反映现实。**目标是 Collaborating（合作 + 坚持）**——不要妥协，不要竞争，不要回避或迁就。（录像在此结束。）

## 核心要点速览

1. **课程定位**：COMP9820 是 Basem 为 COMP9900 capstone 设计的"预备课"，重点是业界实际使用的 Agile/Scrum 实践与工具（Git/GitLab、CI/CD、部署），不教编程语言。每年 T1/T3 开课，要提前规划选课。
2. **没有考试**，全部考核围绕一个 6 人团队、三个 sprint 的项目：Demo 35% + 团队报告 45% + 个人报告与互评 15% + 个人反思 5%（等价于 Sprint 25/25/30 + 个人 20）。
3. **关键日期**：Sprint 1 第 2–4 周，Sprint 2 第 5–8 周（第 5 周准备变体，第 6 周 flexi），Sprint 3 第 8–10 周；团队 demo + 报告在第 4/8/10 周 lab 内交，个人报告 + 互评顺延一周（第 5/9/11 周）。
4. **出勤强制**：只能参加自己的 lab；**无获批 Special Consideration 缺席 demo = 0 分**。SC 须在截止后 3 个工作日内申请，结果邮件发给 Ghadir Alselwi。
5. **组队**：第 1 周 lab 组队，最迟第 2 周初定组；5–6 人，5 人组会被补人；用技能自测和 Moodle 组队指南；**技术与性格平衡，别凑三个领导者**。
6. **项目**：Sprint 1 全体做 "Shared Expense Splitter"，Sprint 2/3 选变体（餐厅/合租/旅行等）并在原有基础上扩展；导师兼任"客户"角色。
7. **沟通**："Discourse first and last"，先搜后问；私密问题用私密帖或找导师/课程邮箱；lab 内每组有专属导师时间。
8. **AI 政策**：Simple Editing Assistance 级别——**禁止生成式 AI 写/补全/审查/调试代码或生成/改写报告**；GitLab 历史可能被查，团队连带负责。
9. **AI 时代的核心能力**：理解流程和实践、能领导团队（包括 AI agent）、在团队环境中用一套工具协作——这是本课要练的，也是面试时"为什么还需要人"的答案。
10. **软件工程 ≠ 编程**：从规格到维护的全流程工程学科；四类活动（规格、设计实现、测试、演进）；软件失败代价巨大（英国航班事件）；设计时要考虑长期演进。
11. **瀑布 vs 敏捷**：瀑布顺序、各阶段追求完美、不处理不确定性、后期改动昂贵；敏捷迭代增量、需求可演进、短 sprint、持续反馈。本课用 Scrum，三个 sprint 就是三次迭代。
12. **Git 心智模型**：工作目录 → 暂存区 → 仓库；本地 vs 远程；commit 是快照，**commit message 必须写清楚**。
13. **团队 Git 流程**：pull → 分支 → commit → push → merge request → 评审 → merge；main 始终可运行；merge 前构建测试。
14. **GitLab**：gitlab.cse.unsw.edu.au 用 SSO 登录；仓库由课程组第 2 周前建好；SSH 免密；第 1 周 lab 动手练习 Git。
