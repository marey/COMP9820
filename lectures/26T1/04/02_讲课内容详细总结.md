### 13:20–17:05 引入：反馈也来自代码；手动测试的局限

- 软件管理强调**反馈、短迭代、按反馈改**。反馈不只来自用户/客户/利益相关者，也来自**代码和项目本身**：有没有 bug？软件是否在做你想让它做的事？你希望**尽早**得到它——方式之一是**测试**。
- 演示 Sprint 1 的 Task Tracker：加一个任务→出现了→删掉→没了，这就是测试。学生的做法：什么都不填点 add 看反应；用 print 看 tasks 列表变没变。都是验证，但都**手动**。能不能更快、更容易、更少手动？——"自动化"。今天就讲怎么让测试更容易、更快、更频繁、更可视化。

### 17:05–22:20 TDD 是什么、为什么先写测试

- **反馈速度很重要**，TDD 是加速反馈的一种方式。**TDD**：先写描述期望行为的测试 → 运行（失败，因为还没写生产代码）→ 写最少的代码让它通过 → 小步重复。
- 用 Task Tracker 类比：假设还没实现 add，点 Add 任务不会加；还没实现 delete，点 Delete 不会删——测试就是先描述"应该会加/会删"。
- **为什么先写测试？** 学生：更早犯错、更早改正。讲师补充：
  1. 呼应上周用户故事——一切从用户价值出发，先想"要达成什么"，再实现细节：**先设计、先规划，再做**。
  2. 测试是**活文档**：不用另写文档，读测试就知道软件能做什么；将来改生产代码（更优雅、加注释）时测试不变，跑一遍就知道是否还符合预期。
  3. **少偏见**：先写实现再写测试，脑子里已经有了"应该怎么工作"的假设；先从故事写测试，测的是**预期行为**。
- 线上问：standup 说"15 分钟"是要开视频会吗？——不是，Teams 频道发消息即可，只是强调要快（Sprint 1 每周 2 次、Sprint 2 每周 3 次，不该耗时）。

### 22:20–27:30 什么是测试；pytest；项目结构

- **测试是检查应用行为是否正确的代码**：通过→绿，失败→红。例：加载 index 页，检查响应里有某任务名。
- 示例测试 `test_index_shows_tasks(client)`：`client.get("/")`，断言 `b"Complete Flask tutorial" in response.data`。做这个**不需要启动服务器、不需要 UI 能用**——项目只实现一部分、前端还不完善时也能先写测试。
- 测试放哪、怎么跑？Python 已有现成框架 **pytest**：`pip install pytest`（mac 用 `pip3`）；它自动找到所有 `test_` 开头的函数并运行。
- 建议建 `tests/` 文件夹归类（非强制，只要有 `test_*.py` 就能找到，但分文件夹结构更清晰）。

### 27:30–32:00 现场演示：跑 pytest、分组、失败长什么样

- 终端 `pytest` → `collected 1 item` → `1 passed`：意思是向 `/` 发请求，响应里含那一行。
- 加更多测试并用 **class `TestIndex`** 分组：测试很多、列表很长时用 class 做高层分组（都是关于 index 页的）。再跑 → `3 passed`。
- 故意加 `assert b"hahahaha" in response.data` → 输出 `..F`：绿点=通过，红 F=失败，并指出**哪个测试哪一行**失败。于是判断：是测试写错，还是实现缺了/错了，回去改实现。
- 正常流程：**先写测试用例（不写实现）**。其他可测行为：输入为空点 Add，会不会加一个空白项带 Delete 按钮？先写成测试，再写实现。

### 32:13–35:20 conftest.py 与 fixture

- **`client` 是什么？** 不用真正跑服务器，pytest/Flask test client 帮你测"给定请求→是否得到特定响应"，框架已实现。
- `client` 定义在 **`conftest.py`**（文件名**必须**如此，pytest 自动找）：定义初始任务 `INITIAL_TASKS`，并**每个测试前重置**。这很重要——前一个测试删了任务，后一个测试查"数量加一"就会被影响；测试之间不能互相影响。放进 conftest 的重置会**自动对每个测试触发**，这是 pytest 的强大之处。
- 第一次学测试会觉得很"虚"——**动手写才会越来越清楚**，需要练习。

### 35:20–41:30 Test Structure 语法；课堂互动"明天怎么做"

- 课件补充语法：class 内用 `self`；函数名必须 `test_` 开头；`client` 由 pytest 注入；`response.data` 是页面内容（**bytes**，所以断言用 `b"..."`）。
- **"明天做项目，按 TDD 下一步做什么？"** 学生：写测试用例。讲师：看**用户故事**，用故事写测试。一开始可能不全面（只测 index 显示 + add 主功能），后来发现**边界情况**（空输入点 Add 应保持不变）再补——从故事出发、先主要用例、逐步补边界。
- **"是先写完所有测试再写所有实现吗？"** 不是。先核心测试→写实现→随时发现缺测试就补。
- **"测试能过了但想重构，先改还是先保证通过？"** 先用**最少努力**让测试通过，之后有时间再重构；首要目标是通过。
- **"我很确定要做多用户、很清楚怎么写，能先写代码再补测试吗？"** 学生们："还是先写测试。"讲师：对，**再自信也先写测试**。

### 41:30–44:50 More Behaviours 与 The Rule

- Add / Empty / Delete 各一个 Red→Green→Refactor→Repeat 循环。"空任务不添加"Sprint 1 不要求，Sprint 2 可作为故事：先写"POST 空任务后数量不变"的失败测试→实现忽略空/纯空白→重构→重复。可以一次写几个测试，但不必写完所有。
- **规则：没有失败的测试就不写生产代码。** 早期开发者常见错误："以后肯定用得上这行代码"——对未来的假设往往落空；代码越多要维护越多、bug 越多、将来改动越麻烦。**不要写"假设将来会用"的代码**；只写刚好够通过测试的代码。想要什么行为？答案在**用户故事**里。测**行为**不测实现（也是先写测试的原因）。

### 44:50–49:35 Why TDD？全绿≠没 bug；结束 4.1

- **Design from the outside** = **黑盒测试**：不管盒子里怎么工作，只管表现——像开车不用懂发动机。
- **Living documentation**；**Safe refactoring**：学生答"代码更少"；讲师：功能间有依赖，改 A 可能无意影响 B，跑 pytest 会测所有，所以改动更安全，**每次改完就跑**；**Confidence and control**。
- ⚠️ **"pytest 全绿，能说软件做了你想要的吗？"——不能。** TDD 不防错，测试可能**不全面**（忘了测空输入）。全绿只说明**你测的**都对——它**揭示** bug，不**防止** bug。
- Common Misunderstanding / Order（洋葱由内向外）两页已讲过。
- 讲座只能讲高层的"为什么/是什么"；**怎么做**必须自己写测试、练流程，之后会有更深理解和更多问题——很正常。休息至 19:00。

### 57:17–1:04:05 休息后 Q&A：Sprint 2 做什么功能、评分基线

- Sprint 1 大家做同样功能（add/delete）是因为还没学故事；**现在 Sprint 2/3 由你们自己的故事决定功能**，课程不会规定"加登录/加用户"。指南这部分仍在起草，最迟明天发布；sprint 末按**给用户带来的价值**评分。

- "一起创造这门课"：首次开课，任何反馈都欢迎。

### 1:04:05–1:10:10 CI 引入与 GitLab 演示

- 有了测试，但还得**手动**跑 pytest，有时会忘、bug 溜走；队友也未必好好跑。怎么让每个人**频繁、轻松**得到反馈？——**pipeline**，属于**持续集成**。
- **CI 定义**：自动化地把多个贡献者的代码变更集成到单一软件项目——关键词：自动化、代码变更、多贡献者、单一项目。具体说：让合入 main 更**频繁、稳定**。简化理解：**每次 commit 自动跑 pytest**，并在 GitLab 上给出可视化 OK/Not OK 及详情。
- GitLab 演示：项目列表里 commit 旁的**绿勾/红叉**。绿勾 → pipeline 详情：分**阶段（stage）**——必须先过一步才能下一步，或几个测试并行；这里只有一个 job、其实什么都没测只是打印，Job succeeded。红叉（Lecture_Slides 项目 deploy 阶段 pages job 失败）→ 日志显示错在哪。
- **每次 commit、每个 MR 都自动跑全部测试**，全组可见，可互相支持。**合并 feature branch 到 main 前先确认绿勾**，不要把坏代码合进 main。
- 休息时另一问："要写文档证明测试先于实现吗？"——**不用**，**git 历史就是文档**：先提交测试（message 写清楚），再提交实现。

### 1:10:10–1:14:35 Setting It Up：.gitlab-ci.yml

- 每个 git 平台（GitLab/GitHub/Bitbucket）有自己的 CI 方式；GitLab 是在仓库根目录加 **`.gitlab-ci.yml`**，**文件名必须完全一致**。**YAML** 像 markdown，是**数据**文件，不可运行。
- 讲解示例文件：**stages**、**job**（名字自取，发生在 test 阶段）。为什么分阶段：本课只讲 test、deploy，现实中测试前有 **build**、后有 **deployment**，只有前一阶段过了才进下一阶段。**script** 是真正执行的动作——示例只是 `echo`/`sleep`（code coverage 下周讲）；我们要放的是 **`pytest`**：pipeline 触发时运行 pytest。

### 1:14:35–1:20:00 演示：Pipeline Editor 添加 pipeline

- 加 yml 的两种方式：直接 add file；或 GitLab UI **Build → Pipelines → Pipeline editor**（提供模板、指引、文档链接，含 build/test/lint/deploy 等示例 job——本课只需 test）。
- 编辑器有**语法检查**：YAML 对缩进/空格非常严格，多一个空格就报 invalid。讲师删多了也报错（build-job 引用了不存在的 build stage）→ 只留 `stages: - test` 和 `unit-test-job` → "Pipeline syntax is correct" → Commit changes。
- **commit 或 MR 都会触发 pipeline**。提交后项目页出现 Running 状态按钮；点开看进度（拉 docker 镜像等）。等约 1 分钟 → Job succeeded → 绿勾。
- **为什么 GitLab 能跑你的代码？** pipeline 跑在一台**服务器/runner**上——另一台机器拿到项目代码并运行 pipeline。

### 1:20:00–1:22:50 Runner 的工作方式与注意事项

- 所有项目**共享 runner**（一台跑所有 job 的电脑）。组里多人 push 同一仓库，多个仓库又共用同一 runner，所以有时很慢：刚才排队 1 秒、跑 1 分 5 秒算快；测试多会更久，很多人同时用会很慢。**不要在截止前最后一刻集中 push**——所有组都在用同一 runner，会排长队。
- 在**个人**项目里练可能提示 "no runner available"；**COMP9820 下的项目都能用**，CSE 配了 runner。GitHub/Bitbucket 有一批 runner，超免费额度收费，你们不需要。

### 1:22:50–1:25:20 Configuring：把 pytest 加进 pipeline

- 要让 runner 能跑 Python：用 **Python image** 并指定版本（`image: python:3.11`）——**全组同一版本**，避免"我电脑能跑他电脑不行"。
- **before_script** = script 之前运行的命令：`pip install -r requirements.txt` 先装依赖，避免依赖缺失导致测试失败。**script**：`pytest`。
- 可选：`only: - main` 让 pipeline **只在 main 分支跑**——feature branch 多、每个 commit 都触发会慢，可只让合入 main 的 MR 触发。看你们组情况；其他配置课后探索。
- 要求：`requirements.txt` 在根目录（含 pytest 和 Flask 等）；测试在 `tests/`。push 后 test job 在 runner 上跑，pytest 过则绿、失败则红。

### 1:25:20–1:30:10 演示：push 与 MR 触发 pipeline

- 改项目前先 **`git pull`**；粘入 yml；`git status` 看改动（yml、app.py 端口、删掉 hahahaha 测试）；提交前 **`git add`**——比逐个加文件更省事的是 **`git add --all`**，但**只在确定要把这些改动放同一 commit 时用**。`git commit -m "ready to demo ci"` → `git push` → pipeline Running → Passed；日志显示安装 Flask 等依赖、`$ pytest`、`3 passed`。
- **MR 也触发 pipeline**：新建 MR（main → 实验分支）→ MR 页显示 **Pipeline passed** ✅ + Ready to merge（起初没显示是在等 runner）。**点 merge 前要看到绿勾**；审查队友 MR 时**确认绿勾再 approve**；提交者合并时也再确认。讲师没真合并（怕搞乱仓库）。

### 1:30:10–1:33:15 总结、进一步阅读、收尾

- **CI 总结**：写测试 → 写实现 → push 到 GitLab + 开 MR → 确认绿勾 → 放心合并。
- **重要规则：main（master）永远是绿的**，没绿勾不合并。
- 进一步阅读：GitLab CI 文档（视频、文档）、Atlassian CI 教程（关于 CI、GitLab、Git 的资源都很好）。讲师难得提前讲完。
- 线上最后一问："是不是不用课外开会、每周会议可以在课上开？"——**没说不用课外开会**，很多组发现课外开会很有帮助；只是课上开能省时间（人齐）。**每周一次会议是最低要求**。

## 三、核心要点速览

1. **反馈来源不只人，还有代码本身**（有没有 bug、是否按意图工作）；要尽早拿到，手段是**测试**；手动点页面/print 是测试但慢，要**自动化**。
2. **TDD**：写一个失败测试（Red）→ 写**最少**代码让它过（Green）→ 重构 → 重复。**没有失败的测试就不写生产代码**；不写"将来可能用到"的代码。
3. 先写测试的理由：从用户价值出发**先设计再实现**；测试是**活文档**；**减少偏见**（先写实现会带偏测试）；测**行为**不测实现（黑盒）。
4. **pytest**：`pip install pytest`；自动运行 `test_*` 函数；用 `assert`；`tests/` 归类；`conftest.py`（文件名固定）定义 `client` fixture 并**每个测试前重置数据**，避免测试互相影响；class 用于分组；`response.data` 是 bytes 所以用 `b"..."`。
5. 不需要启动服务器或 UI 就能测；输出 `.`=过、`F`=败，并指出失败位置。
6. **测试从用户故事来**：先核心/主路径，再补边界（洋葱由内向外）；不是"写完所有测试再写所有代码"；**再自信也先写测试**；先让测试过再重构。
7. **全绿 ≠ 没 bug**：只说明你测的都对；TDD 揭示 bug，不防止 bug。
8. **CI**：自动把多贡献者的变更集成到单一项目，让合入 main 更频繁、稳定；简化说就是**每次 commit/MR 自动跑 pytest** 并在 GitLab 显示绿勾/红叉。
9. GitLab CI = 仓库根目录的 **`.gitlab-ci.yml`**（名字必须一致；YAML 是数据文件、缩进严格）：`stages`、job、`image: python:3.11`（全组同版本）、`before_script: pip install -r requirements.txt`、`script: pytest`；可选 `only: - main`。Pipeline editor 有模板和语法检查。
10. **Runner** = 专门跑 pipeline 的另一台电脑；CSE 为 COMP9820 项目提供共享 runner（个人项目可能没有）；共享意味着截止前集中 push 会排长队。
11. **main 永远绿**：MR 合并前（审查者 approve 前、提交者 merge 前）必须看到 pipeline passed。
12. "测试先于实现"的证明是 **git 历史**（先提交测试再提交实现），不需另写文档。
13. Sprint 2 要求：每周 ≥1 次全员会议 + 纪要；每周 3 次 standup（≤15 分钟，Teams 消息即可）；MR 必须 `Closes #X` 链接 issue（labels/milestones 可选）；CI pipeline 必做；功能由**自己的故事**决定（评分标准明晚定稿，欢迎反馈）；截止 **Week 7 周一 12:00**，Week 7 lab 全员 demo。
14. Sprint 1 retro 可迟交至本周 class 前（仅此一次）；teamwork contract 是**规划**（怎么协作），retro 是**反思**。有疑问及早发论坛/邮件，反馈表用于长期改进。
