## 一、一句话总览

本讲的主线是 **"Why Agile → What Agile is → How to be Agile → 在本课程项目里怎么落地"**：讲师先用 90 年代软件危机解释瀑布/重流程为何失败、敏捷宣言为何有效；再澄清 Agile 不是流程而是哲学（适应性 > 预测性、以人为本 > 以流程为本）；然后给出可操作的起点——Sprint、Teamwork Contract、Standup、Weekly Meeting、Issue Board、Pair Programming、冲突处理；最后走读 Sprint 1 指南、评分标准、提交规则，并用"餐厅"比喻讲解 Flask starter code 的前后端与路由。

## 二、按时间顺序的详细内容

- 展示 **Lecture & Resources 页**：每周有 Topic、Slides（课前上传）、Livestream/Recording（YouTube 与 SharePoint 两份相同）、Other resources。Week 1 资源：Git Practice（如何写好 commit、好 MR）、Lab_Git。
- 本周计划：展开讲 what/why/how Agile；讲项目——Sprint 1 指南、starter code、Sprint 1 期望。相关资源：Standup Guide、Sprint 1 Guideline、Setting Up Guide、Teamwork Contract、Help Sessions。

### 00:11–00:14 为什么学 Agile / 学生对 Agile 的理解

- 所有课的结构都是 **Why → How**：解释为什么重要、怎么做。
- 学生回答对 Agile 的理解：把大项目切成小块并保证每块带来价值（讲师："这是一个关键原则，但 Agile 不止于此"）；更现代、更灵活；没有严格规则（讲师："其实还是有规则的，只是不像瀑布那么严格"）；不那么重文档；更喜欢灵活变化，像创业公司。讲师：都对，但 Agile 比这更多。
- 提到常听到的术语 sprint、scrum master 都源自 Agile，但 Agile 不止这些。

### 00:14–00:18 Agile 的起源：软件危机

- 90 年代"软件危机"：近 1/3 项目被取消，大量延期、超预算、交付不足；"当时我们学院也很挣扎"（笑）。
- 组织的应对：加文档、加签字审批、加质量控制、定义更严格的阶段——即**瀑布 / Phase-Gate**：需求 → 设计 → 编码 → 测试 → 上线 → 维护，阶段间有严格的准入规则。
- "项目失败？加流程。"——**有效吗？没有。** 对其他工程学科合理的做法，在软件上没奏效。
- 于是一群开发者聚在一起寻找新方案 → **敏捷宣言**。

### 00:18–00:27 敏捷宣言四条价值观与课堂讨论

- 四条价值：个体与互动 > 流程工具；可工作软件 > 面面俱到的文档；客户协作 > 合同谈判；响应变化 > 遵循计划。"完全不同的方案，而且**它奏效了**。"
- 强调：这**不是流程，不是方法论，是价值观**；右侧仍重要（仍有流程、工具、文档、计划），只是左侧更优先。
- 课堂讨论"为什么瀑布不行而这个行"：
  - **少官僚 / 少签字**：不必层层找经理审批，省时间；但 review 仍重要，**责任由所有人分担**，而非只有经理负责。
  - **客户反馈**：反馈应来自真正的用户，而不是"自认为懂用户"的经理——现实中经理和开发者常常并不真正理解用户需求。合同是一开始谈定的，可能已不反映真实需求。
  - **响应变化**：变化来自多处——开始时误判需求（后来发现某功能不重要、另一被忽略的更重要）；世界变化太快（尤其 AI 时代），六个月后用户需求已变；**团队人员变化**（会写代码的骨干离开、新人带来新技能）。要尽快响应，而不是抱着合同找经理签字——"在敏捷世界里人人都是经理"。
  - **可工作软件 > 文档**："你们喜欢写文档吗？"没人喜欢，且极耗时；文档本身不给客户带来价值，所以把精力放在带来真实价值的事上。但仍需**基础文档**（如何运行代码），对新成员上手很重要。
  - **个体与互动 > 流程工具**：人是一切的中心——不只是客户与经理，是团队中每个人。每个小组的偏好、技能、协作方式不同，要找到最适合本组的方式；工具再高级，人不用也没用。仍有工具与流程可以帮助人，但人更重要。
  - 计划仍重要（毕竟是工程项目），但**计划可以改**。

### 00:27–00:29 关键澄清：Agile 是哲学

- 没有统一的"理想方法"、没有唯一正确的敏捷流程。Agile 是价值观、原则、哲学——一种思考软件开发的方式。它不是工具、不是清单、不是框架、不是"可以做"的东西。**你不能"用"Agile，只能"成为"Agile。**
- 学生可能觉得"没有流程可照做，太难了"——但可以练习，后面会给出起点。
- 总结为两条原则（Martin Fowler）：**适应性而非预测性；以人为本而非以流程为本。**
- 为什么传统方式失败：它说"照计划做就成功，不照做就失败"——但计划本身可能是错的、需要改变。敏捷更灵活，强调**交付价值**而不是符合计划：不问"我们照计划做了吗"，而问"我们交付价值了吗"。

### 00:29–00:35 以人为本：什么样的团队会成功

- "人是软件成功最重要的因素。"提问：什么样的团队最可能成功？学生：一起协作；按各自技能贡献。讲师："很高兴你们没说'全是天才'。"——**多元化团队**（不同技能、不同学习目标）比全是编码专家或全是用户体验专家的团队更可能成功，而且要乐于协作。
- 重要的不只是技能，还有协作质量、**心理安全**、动机、沟通、信任。
- **Psychological safety**：Google、Amazon 等都在谈——人们**敢于开口**。对计划有顾虑就说，别想"我不是最聪明的，他们一定是对的"。好团队让每个成员都敢说话：鼓励发言，别人说顾虑时耐心倾听。不是编码最强的人可能在别的方面更强。如果有人说"我最聪明，都听我的"，别人会觉得无法贡献，最后你只能一个人干、只有一套技能——没人能样样精通，所以要协作。
- **沟通**的含义：敢说；**频繁、定期**；让大家在同一页；与心理安全相关——10 周里有几天状态不好、没进展很正常，告诉队友、互相求助与支持；**透明**——卡住了立刻说，否则别人以为你在推进，到 deadline 才说"我卡了一两周"就太迟了。
- **流程服务于人**：找适合人的流程和工具，而不是人去迁就工具。

### 00:35–00:40 How to be Agile 与 Sprint

- 成为敏捷需要真实经验，很模糊——所以给出可起步的实践，再由各组定制：每日计划、迭代、回顾、快速反馈、持续集成、任务/测试驱动开发。今天讲 sprint 与 teamwork；retro 下周；其余在 Week 5–7 左右逐一讲。
- **Sprint**：固定时长（一周、两周或稍长，通常很短）；不必规划明年，只规划最近一两周——因为未来会变，近期最优先的才最重要；为该 sprint 设定任务；结束后在组内互相反馈/review（这周怎样？工具合适吗？流程要改吗？）并设定下一 sprint 的任务。**时间固定、范围灵活、只规划下一 sprint、每个 sprint 末通常有发布。**
- 每个 sprint 末要**带来价值**；本课不做真实 release，而是 **demo** 给 tutor（扮演客户）："你带来了什么价值？"
- 学生问"要测试代码吗？"——Sprint 1 还没讲测试；展示价值的方式就是向 tutor 演示项目能做什么。

### 00:40–00:48 Teamwork Contract

- "刚说不要合同，现在又讲合同？"——这是**活文档**，随时可改；敏捷不等于没规则。契约写明期望与责任，存放在仓库，全员同意。
- 课程网站有模板，不必严格照抄，只是帮你起步；找最适合本组的形式。
- 模板讲解：
  - **Purpose**：为如何协作、沟通、交付设定清晰期望；作为活文档更新。
  - **Team Members & Skills**：传统做法是给每人角色（经理、前端、后端、产品负责人），业界仍常见；但敏捷强调**技能而非角色**，责任共担——不是"我是前端就不管后端"。建议用"主要技能 + 附加技能"，可以写**想学的技能**（如想练客户技能、管理/领导技能）。三类技能：Customer（理解用户需求、产品管理、需求收集、UX）——下周讲需求，Sprint 1 有相关交付物，建议每组至少一人侧重；Development（编程、测试、设计、架构）；Coaching（引导、辅导、流程改进、协调）——协调会议、发起站会，锻炼领导力的好机会，不必是最会编码的人。每个 sprint 可换侧重，但要覆盖所有方面。
  - **Communication Plan**：**强烈建议 MS Teams**——tutor 能看到；用 WhatsApp/Discord 的话，日后有冲突课程无法查证（希望用不上）。设定会议时间让大家锁定日历；设定响应时限；提前想好缺席怎么办。
  - **Work Distribution**：如何分配、有人完不成怎么办、是否要 code review。
  - **Ground Rules、Conflict Resolution**：提前想好冲突如何解决。
  - **Quality Standards**：Sprint 2 再详细讲，Sprint 1 先写自认为合适的。
  - **Contract Updates**：Sprint 1 内更新没问题，但要有**历史记录**（改了什么、为什么）。
- 契约是 Sprint 1 交付物之一，本周 lab 可开始，tutor 可帮忙。

### 00:48–01:03 Standups

- 定义：频繁（常为每日）的简短进度更新。**不一定是真正的会议**——传统是每天 10 点大家坐会议室；现在各自在方便的时间更新（讲师早 8 点，夜猫子 12 点），更灵活。
- 三个问题：做了什么、遇到什么问题、接下来做什么。
- **为什么重要**：让大家在同一页；更关键是**尽早暴露并解决障碍**——团队工作互相依赖，我卡住会让等我的人也卡住；"接下来做什么"让队友能据此规划。
- 时长：每天最多 15 分钟，2–3 分钟足够。
- **Sprint 1 只要求每周两次**（任务少、依赖少，不要求每天）；一次可在 lab 上当着 tutor 做（tutor 反馈进度、帮解 blocker、了解小组运作），另一次自行安排。可做三次（一三五）。
- **学生提问：如何对待不交东西的人？** 讨论：绩效改进计划（"太正式了"）；查 Git 贡献（讲师另一门课这么做，但本课贡献方式不止编码）；跳过其部分；找 tutor。讲师建议：先联系（Teams、邮件）；**24–72 小时无回应先担心安全**——讲师上学期曾因学生 72 小时失联叫了保安；报告 tutor 核实；然后**跳过其工作继续**——把小组当创业公司，个人成功不算成功，**小组在 sprint 末交付价值才是目标**，从目标倒推；计分问题找 tutor，安全问题找讲师/tutor。
- 站会**不是给 tutor 的状态汇报**，是团队自己对齐；不是长会（不是 50 分钟）。
- Standup Guide 示例（John/Sarah/Mike/Lisa/David 的 Yesterday/Today/Blockers）：示例里写了角色，你们不必写；**必须有 Action Items**——发现 blocker 就要有行动，否则站会只是一份文档。需要指定一人（通常想练领导力的人）发起站会。
- 质量：要具体（"写了 2 个用户故事"而非"做了些东西"）；没 blocker 写 None；卡住要透明。坏例子：太长（没人读）、太模糊（"昨天做项目，今天继续做"）。
- 发起者要确保人人参与，不参与的私下提醒，但不能强迫。
- 学生问形式——异步在 Teams 发帖即可（"asynchronous，好词"）；想开同步会议也行，保留会议纪要/录音即可。
- Tips 与 Red flags 留课后读。
- **计分**：tutor 需看到每周至少两次且每个人参与；**站会按个人计分**。**从本周开始**，时间自定。

### 01:03–01:05 Weekly Meetings（随后休息）

- **Sprint 1 不要求周会**（事情少）；**Sprint 2 起每周至少一次**——相当于更长的站会：可结对编码、讨论、规划、一起解决问题。站会异步、周会同步。可在 lab 上开。需要**会议纪要**（出席人、可选议程、讨论要点、行动项），形式灵活。
- 休息约 6 分钟（实际录像间隔到 01:18）。

### 01:18–01:22 GitLab Issue Board 演示

- 向线上同学道歉忘了打招呼。演示：在小组项目 **Plan → Issues → New item**：标题 "Feature: adding tasks"，描述可列 research Flask、backend for adding tasks、frontend——但**建议拆成多个小 issue**（一个 research Flask，一个 backend…），更易跟踪。
- Issue Board：Open/Closed 列，可拖动；本周下次会议就可开始用——例如我想练开发技能，就给自己分配相关 issue，并指定别人 review。
- 学生："像 Jira。"——对，像 Jira/Kanban 的简化版；用 GitLab 是因为与仓库集成，不用另开平台。
- 每个 issue 有编号；在 commit message 或合并 feature 分支时写 `Closes #2`，合并到 main 后 issue 自动关闭，别人也知道这次提交对应哪个 issue。
- 总结：**Issue 代表工作，Commit 代表实现，Merge Request 代表审查与集成——一切连接起来。**

### 01:22–01:23 Pair Programming

- 非必需；如果你的课程目标之一是学编程，可与组员结对：两人一台电脑一个键盘，轮流写、边写边讨论。用于学习目的。

### 01:23–01:27 Handling Conflict

- "有人的地方就有混乱"——最重要的是**持续沟通**（与队友、与 tutor）："沟通能解决大多数冲突。"曾在 Reddit 看到学生说三周没和组员联系——即使没进展、卡住了，也要沟通，让别人知道你的状态。
- 情境讨论：
  - **我比组员懂得多**：休息一下、做别的作业、给他们时间追上；或去学不同技能——本项目可锻炼的技能很多。
  - **组员做得不够**：沟通、沟通、沟通；不行找 tutor；一次不回不代表第二次不回。
  - **组员消失了**：在 Teams 联系确认安全；72 小时无回应就报告（讲师会去联系）。
  - **组员合并了坏代码 / 不找人 review 直接合并到 main**：学生答 revert；问他们为什么——也许不知道 Git 怎么用、不小心合并了，或需要帮助但不好意思问（"没有人是傻瓜，尽管求助"）。私信礼貌请其停止；无改善就邮件 tutor。
  - **组员粗鲁**：礼貌要求停止；无改善就找 tutor。
- 规律：先直接清楚地和当事人沟通；解决不了找 tutor；也可调整自己的计划——保持灵活，**最终目标是项目的价值**。
- 今天讲的一切（站会、issue 等）从本周用到 Week 10。

### 01:27–01:45 Sprint 1 指南与评分

- 时间不够，demo/代码讲解下周继续。问"项目是什么？"——Task Tracker。
- 只发布了 Sprint 1 指南，避免用还没学的内容淹没大家。指南里有**按周计划**：Week 1 加入小组、掌握 Git、理解 starter code；Week 2 写契约、issue board 加任务、按 Git 规范给 starter code 加功能（add & delete）、≥2 次站会；Week 3 规划功能并写用户故事、管理 issue board、sprint retro 含 teamwork evaluation、≥2 次站会。
- 落后一点不用慌——**没有每周交付物**，不会检查"Week 2 做完了吗"；**Sprint 1 截止 Week 4 周一**。
- 本周任务有易有难：**易**——契约、issue board、站会（照做就得分，"超级容易的分"）；**难**——给 starter code 加新功能（尤其无前后端经验者）。但 **Features Demo 只占 30 分中的 5 分**，其他（Git MR、用户故事、issue board、retro、个人分）照样可拿高分；无经验也能拿高分，不必焦虑。可利用 Sprint 1 补前后端知识——web 开发不是本课重点，但讲师每周会教一点，也需自学。做不完可下周继续。
- 下周讲用户故事与 sprint retro。
- **Git practice 极其重要**（重复了六遍"important"）：推到 GitLab 的一切都要遵守（MR、commit message…）。
- **Participation & standups**：Weeks 2–3 每周两次；lab 上一次当着 tutor（tutor 记录出席、可能追问你为什么这么做——确认你知道自己在做什么）；这是 tutor 提供技术与非技术指导（契约、issue board、小组问题）的好机会；有问题尽早提。Sprint 1 最容易得分，Sprint 2 较难，Sprint 3 最难——**Sprint 1 要打好基础**。
- **Teamwork evaluation**：每个迭代末组员互评，不计分，目的是让教学团队了解小组状况、帮小组反思与规划。评价维度：参与度、可靠性、团队健康（不粗鲁、多沟通、帮助他人、倾听、反馈）、工作贡献。
- 学生问 "Git practice 是指什么"——指课程网站 Git Practice 页（好 commit、好 MR 的示例与规范），上周已讲，是对上周内容的总结。
- **评分**：有小组分与个人分；**截止 Week 4 周一 12pm**。
- **提交方式：推到 main 即提交**；取截止前 main 上的最新版本，之后的 commit 不算。例外：站会在 Teams 频道里，不用推仓库（tutor 有权限）；契约等要推到 main。
- **契约文件建议**：在 starter code 中新建 `teamwork.md`——Markdown 易读、有结构、不用花时间排版；推到 GitLab 很合适；**可追踪变更**（改动时 add/commit 并说明改了什么），PDF 做不到。用 PDF 也不扣分，但 Sprint 2 更新时 MD 更方便。
- 不要等最后一刻才推（讲师以前教 1000+ 人的课，deadline 前服务器被挤爆；本课规模应该没问题）。
- **Sprint 1 无迟交；即使有 special consideration 也不延期**——延长 Sprint 1 会吃掉 Sprint 2 的时间（Sprint 2 紧接着开始）；有批准的特殊情况在评分时考虑。
- **Demo 在 Week 4 lab，必须到场**，缺席该 sprint 记 0（除非批准的特殊情况）——目的是确认工作是你自己的；也是 tutor 反馈、帮助规划下一 sprint 的机会。**非正式**，不用准备演讲：展示项目给客户带来什么价值、如何做到、为什么这么做。
- **学术诚信**：常规要求；特别之处——用 AI 辅助（研究等）**必须正式声明**（哪部分代码、以何种方式）；即使用了 AI 也**必须能解释代码**：tutor 可能要求现场改某行、加一行/一个功能；做不到 = 不了解自己的工作 = 抄袭，该 sprint 记 0。

### 01:45–02:00 Starter Code 讲解

- 学生评价 starter code："很整洁。"README 为零基础同学提供了代码理解指南。
- 结构：`app.py`（Python，**后端**）；`templates/index.html`（**前端**）。
- **Web server 是什么**——餐厅比喻：Python 函数像厨房里的锅具（给输入得输出），但用户怎么"调用"它们？需要一个中间人接单：顾客点披萨 → 有人到厨房用工具做披萨 → 送回顾客。**餐厅就是服务器**，函数是厨房工具，用户是顾客。"你可以把服务器想成一个包含很多函数的大函数：发请求，得响应。"
- **发请求的方式**：改 **URL**（演示幻灯片 URL 从 `/2` 改 `/1`，显示不同页）；**点按钮**（课程网站翻页）；**点赞/回复**（Discord 论坛——点赞变色、回复 "hello" 出现新帖）。
- **前端 vs 后端**：前端是看到的东西；改变前端的往往发生在后端——回帖改变了数据库（后端变了，重新打开仍在）；而只切换页面则后端没变，只是换了显示的前端。
- 学生问能否用别的语言/不用 HTML——**必须 Python + HTML**：课程只能提供这些支持；且要保证组内每个人都能贡献，而不只是一两个会 JavaScript 的人。
- **路由**：`@app.route('/')` 定义"收到这个 URL 就返回这个页面"。改成 `/info` 后访问 `/` 显示 Not Found，访问 `/info` 才显示；可再加 `about` 路由返回 `about.html`（templates 里新增）。这是后端最核心的部分：**给定请求，返回响应**。
- **index.html**：开头 `<style>` 是样式（字体大小、颜色），可以改（演示改背景色）；文本 "Welcome to TaskTracker" 可改成 "my super TaskTracker"。但**别追求花哨**——网站再漂亮功能不行也不值；核心目标是给客户带来价值，想用户最关心什么。
- **后端数据**：可在 app.py 定义 Python 列表（`task = ["task 1", "task 2"]`），再把数据传给前端——留作课后研究。
- **Git 纪律**：加功能/改动前先 **checkout 新分支**，**不要直接在 main 上改**；改完发 MR 请队友 review 再合并；**不要合并坏代码**，main 必须始终安全。
- 课后看 starter code；不懂功能也没关系，每周讲一点 web 开发。结束。

## 三、核心要点速览（考试/实践向）

1. **软件危机 → 瀑布/Phase-Gate（加流程）失败 → 敏捷宣言**。宣言四条价值观左侧优先于右侧，但右侧仍有价值。
2. **Agile 是哲学，不是流程/工具/框架/清单**；"You cannot use Agile, you can only be Agile."
3. **Martin Fowler**：adaptive rather than predictive；people-oriented rather than process-oriented。
4. **成功的重新定义**：不是"是否照计划"，而是"是否交付价值"；按时按预算全功能仍可能失败。
5. **人是最重要的因素**：多元技能团队、协作、**心理安全**、动机、沟通（频繁、透明）、信任；流程服务于人（retro 的意义）。
6. **Sprint**：时间固定、范围灵活、只规划下一 sprint、每 sprint 末有发布/demo、组内 review 与反馈。
7. **Teamwork Contract**：活文档、存仓库、全员同意；技能而非角色（customer / development / coaching）；MS Teams；响应时限；分工、review、规则、冲突、质量标准；更新要留历史。
8. **Standup**：三问；异步在 Teams；具体、简短、透明；要有 Action Items 与发起人；Sprint 1 每周 ≥2 次（一次在 lab）；按个人计分；不是给 tutor 的汇报。
9. **Weekly meeting**：Sprint 2 起每周 ≥1 次，需会议纪要（出席、议程、讨论、行动）。
10. **Issue Board**：拆小 issue；Issue=工作、Commit=实现、MR=审查集成；`Closes #N` 关联。
11. **冲突**：先直接沟通 → 再找 tutor；失联 48–72h 报告并继续推进；目标是 sprint 末的价值。
12. **Sprint 1**：截止 Week 4 周一 12pm；推 main 即提交；无迟交/延期；Week 4 lab demo 必到、缺席 0 分；25 分组分（MR、用户故事、功能 demo、issue board+契约、retro+互评各 5）+ 5 分个人分（commit/branch 3、参与/站会 2）；AI 使用须声明且必须能解释代码。
13. **Starter code**：Flask；`app.py` 后端（路由 = 请求→响应），`templates/index.html` 前端；餐厅比喻；必须 Python + HTML；改动走新分支 + MR，main 永远安全。
