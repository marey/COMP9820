## 时间线

### 00:00–00:02 开场：为什么关心风险管理
- 回顾第一讲：软件项目有大量不确定性——人员变动、需求变化、新技术、新法律法规。
- 风险管理 = 在问题变得昂贵之前预判可能出错的地方；没有预案时，出错会额外消耗时间、金钱、资源。
- 路线图：什么是软件风险 → 为什么管理（成本/信任/声誉）→ 策略 → 证据 → 如何用到项目里。

### 00:02–00:04 回顾：软件项目为什么失败
- 失败大多不是技术原因而是管理原因：沟通差（用户说"帮我解决这个难题"，开发者与利益相关者对"难题"理解不同，方案自然不符预期）、估算差（复杂度、时间）、计划与跟踪弱、风险管理弱。
- 项目成功 = 按时、在预算内、有质量。好的风险管理帮助更早发现威胁、减少返工（一开始就考虑了风险）、让结果"更可预测一些"（不会完全可预测）。

### 00:04–00:07 Foundations：风险、不确定性、机会
- 风险的两个易用定义：① 尚未发生但可能造成损失/威胁成功的问题；② 异常事件/故障 + 对用户/操作者/环境的后果。
- **不确定性** 来自信息缺失（未来有无新技术、有无人员变动）；**风险** = 某事件产生负面影响的概率 + 负面影响的描述，通常源于不确定性。
- 不确定性不总是负面的：新技术也可能让流程更顺——这是 **机会**，风险的反面。
- 风险管理过程：识别潜在问题 → 处理（降低伤害）或消除（去掉负面影响）→ 防止其损害成本、进度、质量、士气。

### 00:07–00:12 风险从哪来
- **外部**：不同利益相关者拉向不同方向（付钱的客户 vs 实际用户想要不同功能，甚至冲突，现实中很常见）；政治因素影响资金/任命（科研项目更常见）。可参考五力模型分析外部威胁。
- **人/协作**：线上协作带来沟通障碍；开发、评审、发布由不同团队负责且缺乏 DevOps 流程与沟通。症状：沟通缺口、认知缺口（团队内部对"完成/正确"看法不同；团队与利益相关者之间也有）、结构问题（评审流程、角色不清、管理团队职责不清）、恢复慢（反馈回路弱）——这就是课程反复强调快速反馈的原因。
- **Task Tracker 中的协作风险**：删除语义不清；对何时保存/更新 JSON 文件的假设不一致；测试覆盖缺口（有人早提出边界情况，有人没意识到）；归属不清（三个 sprint 下来希望已解决）。
- **安全/伦理**：泄露 token/登录信息到代码或日志；隐私与同意（存什么、是否征得同意、怎么存怎么用）；透明性——很多应用现在调用 AI API（如 OpenAI），用户如何、为何看到你给的信息。

### 00:12–00:13 Risk Retirement（风险退役）
- 风险退役 = 风险消失：实现了缓解措施（考虑边界情况、显示错误信息等），或有证据表明风险行为不再发生（消除）。
- Task Tracker 例：风险"持久化可能加载无效状态"→ 加强持久化测试、加更多有意义的测试。

### 00:13–00:17 为什么要管理风险 / 成本收益权衡
- 不管理会失去金钱、信任、声誉、生存能力（例：不合乎伦理/不安全地处理用户数据 → 丢数据 → 失去信任）。
- 好的风险管理：把精力集中在高影响区域（伦理、隐私）；降低 **意外** 失败——失败（如延期）仍可能发生，但要避免"surprise"；要么设法避免（哪怕多花时间做边界情况），要么知道发生时如何应对；加快完成、提高进度可预测性。
- 权衡：风险评估有前期成本，把时间都花在风险评估而不是实现 story 上不对；但早期预防通常比失败后补救便宜（失败会丢信任和声誉，伤害更大）。原则：别花太多时间，但对项目伤害大的风险必须管好。

### 00:17–00:20 角色与职责
- 归属在组织与项目团队之间共享。
- 不是所有项目都需要同样深度：临床应用需要更深评估；小群体使用的小项目可以浅一些。做法：先初步评估，必要时再加严；不必为所有风险写详细计划，聚焦重要的。
- **组织**侧重治理：定基调——"风险管理很重要，这是优先关注领域，这是我们的流程"。**项目经理**侧重日常：本 sprint 的 story 涉及哪些风险，如何处理与监控。
- （快速翻过的页面：组织的典型任务——设定风险文化、定义风险偏好、参与重大决策、监控重大风险、保证小风险也被管理、年度汇报；风险管理目标——防止风险成为重大威胁或返工来源，结合自上而下与自下而上。）

### 00:19–00:24 策略：实际怎么做
- 组织在"接受后果"与"为避免/缓解付费"间取平衡：伤害不大可接受、之后再处理；否则提前花时间和钱规划。
- 两个视角：技术（工具、技术、环境、技术影响）与业务（生产力、利润、性能、需求、预算、商业案例），都重要，应贯穿软件生命周期。
- **四步法**：
  1. **识别** 风险因素（人、协作沟通、隐私伦理、技术）。
  2. **分析** 概率与影响：以"团队对何时保存持久化数据没有一致约定"为例——发生概率高/中/低？发生后影响是什么？
  3. **排优先级**：识别出的风险可能很多，规划每一个都要花时间/钱/资源，用概率×影响挑最重要的。
  4. **制定缓解策略**：降低概率、减小发生后的影响，或两者。
- 另外：定期重访（风险是否退役、是否需提升优先级、是否要调整）；特别关注安全性/安全等软件质量风险。

### 00:24–00:27 示例：并发写入 tasks.json
- 场景：多个用户同时提交任务；或一人删除某任务同时另一人添加同一任务——数据文件会怎样？
- 识别：中等概率、高影响（任务丢失/冲突）——**两者都要给出理由**。优先级高于次要 UI 问题。
- 缓解：保存/合并规则、备份、原子写入——幻灯片只是例子，报告里需要 **更详细** 的缓解计划。
- 有了计划后，改动持久化或部署后仍要重访确认计划有效。

### 00:27–00:29 Evidence Check：风险管理真的有用吗
- 开放问题留给学生。de Bakker, Boonstra & Wortmann (2009) 元分析：几乎没有实证证据表明风险知识真的被用于项目；反事实难证明；利益相关者认知与行为是核心。
- 更相关的问题是 **何时有效**：改变了利益相关者意识；期望与行为根据风险信息做了调整（不只停在纸面，而是真正改变团队行为）；从业者真正关注风险而不是走流程。"很常见的是没人在乎风险管理"——这更像心态/文化问题。

### 00:29–00:32 Sprint 3 风险报告：写什么
- Sprint 3 要交风险报告，需足够可操作：能对应"风险 → 做了什么决策/工作"、"缓解 → 如何知道有效"。
- **每个风险一个块**，必填字段：
  - Risk statement，用公式 **If [cause] then [bad outcome] because [reason]**；
  - Likelihood 与 Impact，并 **justify**；
  - Owner：指定一位或几位组员监控；
  - Mitigation / contingency：失败前做什么、万一发生怎么办，减少对金钱/时间/资源的损失；
  - Evidence：为并发写入加了测试？建了 issue？链接到支持缓解的 MR/commit；
  - Status：open / mitigated / accepted / resolved；
  - Last reviewed。
- 位置：仓库根目录 `RISK_REPORT.md`，从根 `README.md` 链接。

### 00:33–00:35 持久化风险完整示例 + 证据映射
- 风险陈述示例：如果 `tasks.json` 变为无效（损坏的 JSON），应用可能在加载时崩溃，因为 `json.load()` 没有恢复机制。
- 完整行示例：`tasks.json` 缺失/无效/无权限 → 中/高，附可能性理由（首次部署无文件、路径错、只读卷、写入中断截断）与影响理由（核心功能崩、每次加载报错、demo/评分失败）；缓解（校验/捕获 `json.load()` 错误、返回空列表或错误页、先写临时文件再替换、记录权限与 `DATA_FILE`）；应急（删除坏文件恢复、热修复）。讲师注意到这页在投影中没显示完整，说会回头查看。
- 证据放在三处：`app.py`（`DATA_FILE`、`json.load`、`save()`、`/add`、`/delete/<index>`）、`tests/test_app.py`、`conftest.py`（`client` fixture 把 `DATA_FILE` 指向 `tmp_path`）。
- （快速翻过：Status 与 Last reviewed 含义；Avoid / Reduce / Transfer / Retain 四种应对；每个风险 1–2 个监控指标；一个风险块的练习模板。）
- 参考文献：McManus《Risk Management in Software Development Projects》、de Bakker 等 2010 元分析、SWEBOK v3.0。
- 结语：短课、概念不难；请用模板和结构为自己的项目写风险管理计划。

## 核心要点速览

1. **风险 ≠ 不确定性**：不确定性来自信息缺失；风险 = 负面事件概率 + 影响描述；反面是机会。
2. **项目失败多为管理原因**：沟通、估算、计划跟踪、风险管理弱——不是纯技术。
3. **风险来源**：外部压力（利益相关者拉扯、政治）、人/协作（沟通缺口、认知缺口、结构、反馈慢）、安全/伦理（密钥泄露、隐私同意、AI 透明性）。
4. **目标是避免"意外"失败**，把精力集中在高影响区域；预防比事后补救便宜，但要权衡评估成本，不要过度。
5. **归属共享**：组织管治理与基调，项目经理管日常处理与监控；评估深度按项目性质调整（先浅后深）。
6. **四步法**：识别 → 分析概率+影响（给理由）→ 排优先级 → 缓解（降概率/减影响）；并定期重访、关注安全质量风险。
7. **风险退役**：实施缓解 + 证据（测试/监控/评审）表明风险行为不再发生。
8. **证据表明** 风险管理只在改变意识与行为、真正被关注时才有效——它是文化而非文书。
9. **Sprint 3 风险报告**：约 3 个风险，每个一块 7 个字段（Statement / L & I / Owner / Mitigation-contingency / Evidence / Status / Last reviewed），风险陈述用 If…then…because…，缓解标 Avoid/Reduce/Transfer/Retain，证据绑定 `app.py`、`tests/test_app.py`、`conftest.py` 或 issue/MR/commit。
10. **放置**：根目录 `RISK_REPORT.md`，从 `README.md` 链接；模板 `Student_Guide/RISK_REPORT_TEMPLATE.md` 可选；Week 10 lab 正式 demo。
