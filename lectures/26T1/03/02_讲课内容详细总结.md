## 一、一句话总览

本周两个主题：**(1) Software Planning & Stories** —— 敏捷仍然需要计划，但用"用户故事"这种小块、以客户为中心的方式规划；故事的两个特征是客户价值和清晰的完成标准（UAC，rule-based 或 Given/When/Then）；故事从**需求工程四步**（Elicitation → Analysis → Specification → Validation）中来，而不是凭空想象；功能 vs 非功能需求。**(2) Continuous Improvement & Retrospective** —— 用五步法（Prime Directive → 静默头脑风暴 → 静默分组+点投票 → 问"为什么" → 选一个改进目标）做每个 sprint 末的 retro，核心是**心理安全**。穿插大量 Sprint 1 Q&A：功能只需显示/添加/删除，每人都要有 MR，故事和 retro 各交一个 markdown，互评必交。

## 二、按时间顺序的详细内容

### 00:04–00:10 开场：本周主题与 Agile 回顾

- 已近学期三分之一。本周重点：**规划**（为学期余下部分/项目）+ 新内容 **sprint retro**（回顾三周：什么有效、什么要改——因为软件项目管理是 adaptive 而非 predictive）。
- "提到软件项目你想到什么？"——编码、编程。讲师：和一位创业的同学聊天时也发现，很多人以为软件工程就是写代码；CSE 装修入口大图时有人提议以 coding 为主题，同事们反对——编码是基础和工具（AI 也靠它），但 CSE/软件工程远不止于此，重要的是**为人创造真实影响和价值**。今天讲的就是：先知道要给用户什么价值，再决定写什么代码。
- 学生回顾敏捷价值：协作（人 > 流程）、可工作软件 > 文档、迭代（短 sprint、反思改进而非长期计划）。讲师展示宣言：**响应变化优先于遵循计划，但仍然需要计划**——右侧不是不重要，只是优先级低。

### 00:10–00:14 Agile Planning 实践

- 构建系统最重要的部分是弄清要做什么：客户说"做一个 timesheet 管理软件"，你要弄清用户真正需要的价值。
- 六种实践：**Stories**（小块、客户中心，而不是"要这种数据库/前端用什么/后端 Python 还是 JS"——今天的重点：什么是故事、怎么写、从哪来）；**Adaptive planning**（适应性与可预测性平衡，偏适应）；**Visual planning**（用图表达流程，课外自学）；**Planning game**（不讲）；**Real customer involvement**（核心价值，会讲）；**Incremental requirements**（细节在需要前才定——传统做法是长而细的需求文档，涉及安全/金钱/健康的项目至今如此；本课用增量式）。

### 00:14–00:22 什么是故事

- 过去（业界至今常见）大家在一个房间把客户重视的东西写在卡片上："我想管理任务""追踪任务""分配任务"——非常简短，只是引发与客户/用户/团队讨论的提醒。
- 本课要求用 **"As a (role) I want (something) so that (result)"** 模板：业界不一定要求，但它提醒你**把用户放在中心**——从用户出发、以用户能做什么（而非系统能做什么）为中心；"so that" 就是价值。
- 示例（Task Tracker）：As a student, I want to add a new task / display all my tasks / delete a task so that…。角色不必都是 student：group mentor、product owner、lecturer、admin……**第一步是确定产品的用户类型**。
- 两个重要特征：**客户价值**（无实现细节——不谈 bug、数据库、算法）和**清晰的完成标准**。
- 为什么用客户能懂的平白语言？①提醒自己要带来价值；②故事通常**和真实用户一起写**，他们没有技术背景，说"database"听不懂就无法反馈。有时让用户自己写（格式不对再改写）；还可以**让客户帮你排优先级**——想要 100 个功能但只剩八周半，让客户定。
- 坏例子："Add a button to the login page"（太偏实现、看不出价值、客户无法排优先级）；"Add a database table for tasks"（纯技术）→ 改写为 "Allow users to save tasks"。

### 00:22–00:28 拆分故事、特殊故事、最佳实践

- "管理任务"这种大故事太笼统、难排优先级、价值不具体 → **拆分**（checkout 页面也是例子）。三种方式：**按优先级**（create 高、edit 高——你们组可能觉得 edit 不重要，删了重建即可，去问真实用户——delete 中、reminder 低）；**按操作步骤**（create/view/edit/delete）；**按数据边界**（billing info → 信用卡/礼品卡/PayPal）。
- 拆分让你能分别排优先级、任意顺序做；需要练习，有的拆不开没关系；也别拆太小（一小时做完的可**合并**，合并比拆分容易）。
- **特殊故事类型**：不直接体现用户能做什么但仍有价值——demo、文档、非功能、清理、运维/安全故事。
- 最佳实践：非技术语言、客户为中心、用户目标导向、**描述问题而非解法**——工程师（包括讲师自己）常太早跳到解决方案；先识别需求。

### 00:28–00:37 User Acceptance Criteria

- 第二个特征：**清晰的完成标准**——"这两天我做这个故事"，怎么知道做完了能换下一个？所以每个故事在实现前要有 **UAC**（目标导向）。同样用自然语言（客户要审阅、确认、补充"这才是我说的 done"）；实现前可修改（adaptive）。
- 例："As a student, I want to create a task with a due date so that I can track my assignments" → 能输入任务名、能设截止日、创建后出现在列表、显示截止日、创建后收到确认——实现后逐条对照。
- 例：社交账号登录 → Facebook/LinkedIn/Twitter；做完这三个就算完成，UNSW 账号登录不在标准里就不用做（用户没要）。
- 写好 UAC：不太宽不太窄（做几个故事后自然有感觉，再反思调整）；尽量少技术细节（可比故事更技术，但客户要能懂）；开发中可更新。
- 要点式的叫 **rule-based**；替代方案 **scenario-oriented（Given/When/Then）**：Given 前置条件（不在登录页无法重置密码）、When 触发动作、And 同时要做的、Then 结果；结果可成为下一段的 Given（忘记密码示例逐行讲解）。
- 课堂投票：多数人偏好 scenario（更详细、更有逻辑）；rule-based 更简洁、易读易改。Scenario 式更容易转成**测试**（后几周讲）；rule-based 适用于各种故事。Sprint 1 任选，可各练一种。

### 00:37–00:47 课堂练习：学生写故事、讲师反馈

- "monitor the task"→ 好想法但太大，"monitor"含义太多（看待办？看分配给谁？）→ 练习拆分。
- **Q：用户类型有哪些？** 各组自定；通过与真实客户交流或看现有平台的用户来确定；10 周时间有限，**先聚焦 1–2 类用户**，后续 sprint 再加。
- **Q：不知道 Sprint 1 到底做什么、故事从哪来？** ——引出下一主题（需求工程）。
- "As a business manager, I want to add and delete tasks so that I can manage multiple tasks" → add 和 delete 价值不同 → 拆两个。
- "As a customer, I want the tasks described clearly so that I can understand easily" → 典型模糊故事："clearly""easy to use" 无法实现、无法判定完成；很多学生一开始写"我的产品易用、可用性好"——太笼统，要定义清楚易用指什么；问客户过去用其他工具的痛点。
- "As a student, I want to prioritise tasks with colours, and a button to ask questions" → 两件事拆两个故事，并遵循格式："As a student I want to add different colours to my tasks so that I know the priority."
- 结构帮助你识别价值、用户能做的功能、用户类型。更多故事可课间找讲师反馈。

### 00:47–00:51 故事与 GitLab issue 的关系；休息

- 故事听起来像上周的 issue board——关系：**每个故事都放上 issue board 成为一个 issue**；故事是"要构建什么"的规划，issue 是跟踪进度的工具。issue 比故事多（"写团队契约""修某 bug"是 issue 但不是用户故事）。
- 故事不能凭想象——要和客户谈，过程叫**需求工程**，四步：Elicitation、Analysis、Specification、Validation。休息 8 分钟（讲师更新了 Sprint 1 指南，可先看）。

### 00:59–01:09 休息后：Sprint 1 Q&A 汇总

- 休息时对话："一个分支够整个项目吗？"——每人都要有自己的分支，否则怎么合并到 main；分工可以随时改，checkout 新分支即可。
- **Sprint 1 功能要多少？** 要求是 **add & delete task**。UI 要漂亮吗？要邮件确认？数据库持久化（刷新后数据还在）？——**都不需要，最小即可**：能显示任务、能添加、能删除。讲师演示自己的极简版本（My Tasks + Add Task + 三条带 Delete 的任务）："这已经绰绰有余，你们的 UI 可以更简单。"Sprint 1 重点是理解 starter code、练 Git、协作、反思、规划。
- **每人都要 MR 但事情太少？** 自行分工：建议两人做 add、两人做 delete；其他人可合并团队契约、用户故事（每人合并一个故事）。现实中没人为这么简单的 sprint 开五个分支，这样设计是为了**人人练到 Git**。
- **用户类型由组决定？** 是。**Sprint 2/3 建立在 Sprint 1 之上、10 周同一项目？** 是——本周写故事就是在为整个学期规划。**还能改团队契约？** 随时可改，活文档。
- **Sprint 1 到底要什么功能？** 显示、删除、添加，够了——"easy marks"。Sprint 1 是打基础，让有 CS 背景和没背景的人都跟上；建议有经验的同学花时间帮新手，让所有人整个学期都能贡献。
- **项目题目？** Task Tracker（不是 timetable）；把讲师当客户：我有问题和需求，你来解决。**语言？** 后端 Python，前端 HTML/CSS。
- **add 和 delete 分开还是一起？** 分开（不同的事）；而且用户故事要多于这两个。
- **Sprint 2 指南何时发？** Week 4；逐周发布避免信息过载。

### 01:09–01:22 需求工程四步

- 需求不会凭空出现，要推导。RE 是识别系统目的和目标的一系列活动，涉及最终用户、经理、维护工程师等**利益相关方**——不只是用户：还有维护者、领域专家（医疗软件问医疗专家；自动驾驶问隐私/安全专家）。选 Task Tracker 是因为人人用过——组内可**轮流扮演**最终用户等角色。
- **Step 1 Elicitation（获取数据）**：市场调研——GitLab issue board、Jira、Trello 都是任务追踪器，各有优缺点，你用过吗？好用吗？太花哨？你们可以聚焦特定人群（做小组项目的学生、跟踪软件项目的老板），不需要高级功能。**Interview** = 一对一深入交谈、可追问（用 Trello 有什么挑战？你的需求？）；**Focus group** = 把不同背景的人（最终用户、领域专家、懂技术边界的工程师）聚在一起问"如果…会怎样""你遇到什么挑战"。对本项目：访谈同学（同组或同班）、朋友——人人用过任务追踪器；观察（较难，可改为提问）；组内头脑风暴；研究类似工具；问"学生管理任务有什么问题"（如果学生是目标用户——由你们决定）。
- **Step 2 Analysis**：很多人提到同一问题 → 主题/优先级；依赖（先创建才能编辑）；冲突（有人恨某功能、有人离不开）→ 再问为什么、找底层原因。**只为下一个 sprint 排优先级**，不管 sprint 3/4/100。
- **Step 3 Specification**：把数据和分析结果写成用户故事，客户中心语言，每个故事加 UAC，拆分大故事。**只在第一步和客户聊吗？不——始终在聊**：第二步追问为什么；第三步写完再问"这是你要的吗？UAC 漏了什么？优先级对吗？"组员也是客户，开个会就行。
- **Step 4 Validation**：确认没有走偏——回到客户那里问。有了不完美但能跑的功能就拿给客户看"解决你的问题了吗"——频繁要反馈，客户参与是敏捷核心价值。
- **挑战**：需求常在设计/构建开始后才被理解——客户一开始说"太棒了"，做出来一看"不是这个意思/不需要了"→ 所以要频繁回访，及时**停掉不再有效的故事**，别为花掉的几天难过；客户常常**看到产品才知道要什么**→ 做出能用的软件、不求完美、要反馈；客户改主意很常见；开发者不懂领域（有人给非洲某地区做项目却接触不到当地人）；接触不到利益相关方；**太早跳到解法**（先确认问题真实存在，否则在做没有价值的事）。所以只关心下一个 sprint，对利益相关方的理解会越来越好。

### 01:22–01:25 功能 vs 非功能需求

- 课堂上"清晰显示""易用"这类故事不是用户能做的事——它们是**非功能需求**：对系统如何实现的约束（速度、准确率、性能、可用性、隐私），同样重要。
- 例：功能——有新帖或评论时通知所有用户；非功能——邮件在 30 分钟内发出（分配任务后成员应在 30 分钟内收到确认邮件）。产品需求（诊所工作时间内可用、每天停机不超 5 秒）、组织需求（用医疗身份证认证）、外部需求（遵守患者隐私条款）。也要和利益相关方讨论非功能需求。跳过 quiz。

### 01:25–01:33 Sprint 1 指南：2.2 Planning & stories 与提交方式

- 课程网站新增 **2.2 Planning & stories**：(1) Discovery——记录如何做 elicitation（访谈了谁、问了什么、出现了哪些主题）、analysis（如何组织和排优先级）、specification（故事 + UAC）、validation（回访确认"这是你要的吗？我带来价值了吗？"）；(2) 写故事——格式、客户中心、具体可测的 UAC（两种任选）、展示如何拆分大想法；(3) 连接 GitLab——每个故事一个 issue 放上 board。**质量 > 数量**：不需要 100 个故事，过程和质量更重要。
- **提交**：新建 markdown（如 `stories.md`）——演示：先 **`git checkout -b stories`**（不要直接改 main，分支名按组内约定要有意义），创建文件，写内容，add/commit（说明改了什么：加了故事/改了故事）/push——让每个人都有练 Git 的机会。
- **Q：故事的结构？** 可把网站的小节结构复制进 md，各小节写你们怎么做的；线下用卡片做的可以**拍照贴进 md**，不用全部打字——本周 lab 就可以带纸做访谈、写故事、分主题、写 UAC，拍照即可。"能看到你们走了流程、最后有高质量故事并放上 issue board 就够了，不要 20–30 页，我们不想要大量文档。"
- **Q：几个人做同一件事要各开分支吗？** 可共用一个分支，但**每个人在 Sprint 1 都要有一次把 feature 分支合并到 main 的经历**——只是为了练习。

### 01:33–01:51 Sprint Retrospective

- 再看敏捷价值（响应变化、个体与互动）——怎么做到？**反思**：什么有效、什么无效、如何改进；方法是 **sprint retrospective / retro**。目的是改进团队和流程；没有统一标准，每个团队不同。
- 类型：**heartbeat**（最常见，每周/双周，60–90 分钟）——本课每个 sprint 末做一次；**milestone**（更长更深、可能需要外部引导者）——10 周太短不做。周二/三班不建议本周课上做（Sprint 1 还有一周、故事还没写）；周五晚班可在课上做但先写完故事；或另约时间。
- **谁参加**：全员（确保没人掉队）；不要叫 mentor/tutor（除非有冲突），保持私密。**Facilitator**：可轮换（Sprint 1/2/3 各一人，想练领导力可尝试），但第一次建议由项目经验相对多的人担任（不必是业界经验）；不参与讨论只引导；职责：保持进度、确保每个人发声、不参与、**保持中立**（不说我同意/不同意）；做不到就换人；必须保密——营造安全环境（**psychological safety**）。
- **警告**：retro 被用来互相攻击、指责批评、不尊重时会造成伤害——出现就尽早提出、停止 retro，先建立心理安全。
- **时间**：60–90 分钟，第一次可能超时或用不完都正常，流程比计时重要；礼貌地收尾进入下一步；超过两小时太长。
- **五步**：
  1. **Set the stage — Prime Directive**（Norm Kerth）：每人大声读"无论发现什么，我们必须理解并真心相信，每个人在当时所知、技能、资源和情境下都尽了最大努力"并口头同意；有人不同意就停下先解决冲突。来自 *The Art of Agile Development*（讲师展示 O'Reilly 页面）。
  2. **Gather data — 头脑风暴（20 分钟）**：白板（或线上）写 Enjoyable / Frustrating / Puzzling / Keep / More / Less，每人拿便利贴想到什么写什么（不必每类都写），**各自静默**、不讨论，贴到类别下。
  3. **Mute mapping（15 分钟）**：静默把便利贴分组成主题（多人说"每日站会很有效"→ 保持；多人说"应多开一次会"）；一个 sprint 改不了所有主题 → **点投票**（贴圆点或彩笔打勾）选出最想改进的一个。
  4. **Generate insights（10–30 分钟）**：问"为什么"——为什么这个最重要、为什么现状不够好、为什么这样做——理解底层原因，**还不谈解法**。
  5. **Retrospective objective（10–20 分钟）**：想出可能改善的**实验**（一次会改两次会，也许有效也许无效，还有下个 sprint；真实项目一两年有很多 sprint）；**只选一两个**改进（sprint 短、大家忙，改太多会不堪重负）；有人自愿负责跟进（想练领导力的人）。
- **收尾**：全员同意目标，否则换一个或下次再试；把目标加到 issue board；每天检查可能太多，每周 2–3 次即可；站会里加一节反思改进进展。
- **常见问题**：指责争吵 → 先处理团队动态和心理安全，可找 tutor 做外部帮助；改了没效果 → 目标太大就缩小（不必等下次 retro，adaptive）、时间没余量、成员觉得没有话语权；有人不发言 → 害羞没关系，可用站会等其他方式，或是不觉得安全。"我一遍遍提心理安全，因为它非常非常重要。"讲师致歉语速太快，可回看录像。
- **Q：retro 就是 sprint 末的会吗？** 是在 sprint 末的会议里做，但结构更强、专注反思，不是规划或进度同步。**需要记录**：Sprint 1 指南新增 **2.3 Sprint retrospective**——另一个 markdown（又一次每人做 MR 的机会）：checkout 新分支、建文件；可贴白板照片、笔记；写 facilitator 是谁、用时；数据（what went well / challenges / more / less）；insights；**最重要——计划改什么、谁自愿跟进、如何跟踪进度**。

## 三、核心要点速览

1. **敏捷仍要计划**，只是"响应变化 > 遵循计划"；软件工程远不止编码，核心是为人创造价值。
2. **敏捷规划实践**：Stories、Adaptive planning、Visual planning、Planning game、Real customer involvement、Incremental requirements（本课用增量式需求）。
3. **故事**：卡片上的简短提醒，"promissory notes for future conversation"；本课格式 **As a (role) I want (something) so that (result)**；先确定用户类型；两特征——**客户价值**（无实现细节、客户能懂的语言、客户参与写和排优先级）+ **清晰完成标准**。
4. **坏故事**："加个按钮""加张数据库表"、"易用/清晰"这类模糊描述；好故事描述问题不描述解法。
5. **拆分**：按优先级 / 数据边界 / 操作步骤；能分别排优先级、任意顺序；拆不开没关系，太小可合并。特殊故事：bug、文档、非功能、spike、清理、运维/安全。
6. **UAC**：实现前写、自然语言、可修改；**rule-based**（要点式，简洁通用）vs **scenario-based**（Given/When/Then，更适合转测试）；Sprint 1 任选。
7. **Stories → Issues**：每个故事一个 GitLab issue；故事=规划什么，issue=跟踪怎么做；issue 不全是故事。
8. **需求工程四步**：Elicitation（市场调研、访谈、焦点小组）→ Analysis（分组、依赖、冲突、下个 sprint 的优先级）→ Specification（写故事+UAC、拆分）→ Validation（回访确认）；**全程和客户沟通**；挑战：需求在构建后才被理解、客户不知道要什么/改主意、不懂领域、接触不到干系人、太早跳到解法。
9. **功能 vs 非功能**：系统做什么 vs 对如何做的约束（性能、可用性、认证、隐私等）。
10. **Sprint 1 交付**：`stories.md`（discovery 过程 + 故事 + UAC + GitLab issues，质量 > 数量，可贴照片）、`retro.md`（过程、数据、insights、改进目标与负责人）、功能只需显示/添加/删除（无需 UI 美化、持久化）、**每人 ≥1 个合并到 main 的 MR**、Python + HTML/CSS、Week 4 周一截止。
11. **Retro 五步**：Prime Directive（全员朗读同意）→ 静默头脑风暴（Enjoyable/Frustrating/Puzzling/Keep/More/Less）→ 静默分组 + 点投票选一个 → 问为什么（不谈解法）→ 选一两个改进实验 + 志愿者跟进；60–90 分钟；全员参加、无外人；facilitator 中立、不参与、保密、可轮换。
12. **心理安全**贯穿一切：出现指责/不尊重就停止 retro；害羞者可用站会表达。
13. **Teamwork evaluation**：Week 4 周一至周三 Moodle 填写，保密、不计分但**必交**（占 Retro & Evaluation 5 分的前提）。
