### 17:24–19:10 The Course In One Arc
- SPM = 平衡范围、进度、质量、人、风险。
- 四段主线：组织工作与团队（人、Git/MR/issue board、心理安全——retro 里人人敢说话）→ 变化中验证质量（变化太常见；测试、TDD、pipeline）→ 交付与运营（部署不强制但强烈建议做 deployment lab；可维护性、复杂度、好代码原则）→ 治理不确定性（风险）。

### 19:10–30:30 逐条复习"In more detail"（抽问式）
- **Agile 原则**：合作（一群人 > 一个天才）；**适应性优先于计划**（不是计划不重要）。其他的回看第一/二讲。
- Teamwork 核心是心理安全；Git 工作流与 merge conflict 非常常见。
- **需求工程四步**：收集数据（和人谈）→ 分析、找优先级 → 整合（写文档）→ 验证（回到利益相关者验证对 stories 的假设）。
- **测试**：Pytest 做后端单元测试；前端测试超纲但建议了解。
- **TDD**：先写测试再实现；不是全部测试先写完；是黑盒测试——不需要知道实现细节，按 stories/文档写测试。
- **CI**：持续集成，用 pipeline；GitLab 通过 YAML 文件；平台不同逻辑相同。
- **Coverage**：测试覆盖代码的比例，确保没有分支/逻辑未被测试。重要性：找 bug；更关键的是 **改动时确认没弄坏东西**——缺测试的函数被改了就不知道是否还能工作。
- TDD 后代码只是"让测试通过"，需要 **重构**，遵循原则：尽量简单（每行都要维护）；不为未来做假设；coupling/cohesion 一高一低（自己回忆哪个）；清晰优于聪明。
- **持久化**：重启服务器数据不丢（购物车、Task Tracker 任务）；最简单的持久层 = 数据库；最简单的数据库 = 文件，常用 JSON（"内存不是数据库"）。
- **复杂度** 为什么重要：要维护；改动多时少出错/少引入 bug；**估算**改动所需时间、精力、人手、资源。
- **不确定性与治理**：Lecture 8.1 是 30–40 分钟录播，没看的去看，或者读详细的 slides。

### 30:30–35:30 Table Talk：把一个主题映射到 SPM 关注点

### 36:40–39:50 五个模块的关键收获
- **Block 1**：软件系统既是 **社会的也是技术的**——会写代码不等于会做 SPM，两种技能都要有。工具是管理协调与变化的一部分：Jira 更强大；AI 项目管理工具正在出现，讲师未推荐具体产品（不确定成熟度），鼓励自行探索。
- **Block 2**：计划一定会错（"你们没经历过？那很幸运"）。我们是 Agile：每周会议、2–3 周一个 sprint，可以随时回头；反馈回路（计划→行动→回顾）是 retro 重要的原因。
- **Block 3**：质量是习惯——先写测试、TDD、覆盖率、pipeline。
- **Block 4**："在我机器上能跑"不够——要能给别人用，上线后还要能继续管理：重构、加功能、改动。
- **Block 5**：不确定性很常见，如何对它采取行动、管理风险同样重要。

### 39:50–41:15 三大主题配对
- 可追溯性（文档、MR、issue、commit message）、自动化（手工做在大代码库上太慢）、心理安全。
- (a) 关联 issue 的 MR → 可追溯性；(b) 每次 push 跑 CI → 自动化；(c) 无指责地承认错过 deadline 的 retro → 心理安全。
- "Three SPM Themes That Cut Across Everything" 一页一带而过："只是总结刚才说的"。
- Micro-Retro（整学期 retro）留给各组课后做。

### 41:35–48:50 Solo — Three Lines 与分享
- 一个实践、一个意外、下个项目 **第一周** 要做的事。
- **同学 1**（主题：一致性）：每次 merge 前都有一致的 review，检查对他人代码的影响；commit message 变好。意外：即使小项目，大家对同一功能实现方式想法不同（如任务日期时间的结构），要找共同点——解决办法是 **把任务拆得更清楚、各管各的部分**。第一周：全员用 **虚拟环境**，避免库版本问题。
  - 讲师：review 流程极有价值——再努力的人也会漏东西，**一致的 review 流程** 是好实践；拆分工作也是好办法。
- **同学 2**：批准 merge 前问所有人、本地拉下来检查再批准。意外：别人会给出很好的 review 意见、每个 sprint 的头脑风暴都有好主意。第一周：教所有人处理 **merge conflict**——"不要删别人的代码"。
  - 讲师：Git 很棘手，很多学生要好几周才真正理解，讲完≠会用，需要练习和时间；希望下个项目大家都轻松些。

## 核心要点速览

1. **SPM 的本质**：在范围、进度、质量、人、风险之间做平衡；软件系统 **既是社会的也是技术的**——会写代码 ≠ 会管项目。
2. **课程主线**：组织工作与团队 → 在变化中验证质量 → 交付与运营 → 治理不确定性。
3. **SPM 与一般项目管理的区别**：有专门的工具/系统——Git、pipeline 等自动化工具。
4. **三大贯穿主题**：可追溯性（MR、issue、commit message、文档——为了别人和未来的自己）、自动化（无需英雄主义的检查）、心理安全（能无畏地谈错误和风险）。
5. **复习要点**：Agile（合作、适应性优先于计划）；需求工程四步（收集→分析→整合→验证）；TDD 是黑盒、先写测试只写够用的代码再重构；CI 用 YAML pipeline；coverage 的关键价值是改动时不弄坏东西；代码原则（简单、不预设未来、coupling 低/cohesion 高、清晰优于聪明）；持久化最简方案是 JSON 文件；复杂度关乎维护、出错率和估算。
6. **计划一定会错**：靠短反馈回路（计划→行动→回顾）和 retro 纠正。
7. **质量是习惯**："在我机器上能跑"不够，还要能上线并持续管理。
8. **同学总结的实战经验**：一致的 review 流程；拆清任务避免实现分歧；第一周统一虚拟环境；第一周教 merge conflict、不要删别人代码——Git 需要数周练习才能真正掌握。
9. **面试回答结构**："我们的项目表明我能做 SPM，因为 + 证据（MR、测试、CI、部署、风险文档、README）+ 具体例子。"
10. **Portfolio（个人，PDF 即可，≤1000 词）**：做了什么 + 证据（链接/截图/GitLab analytics）+ 反思；本课要求比网上作品集更详细；反思是雇主看重的部分。
11. **Definition of Done** 各组不同，将来写进小组合同（Lecture 9.2 未讲，slides 在网站）。
