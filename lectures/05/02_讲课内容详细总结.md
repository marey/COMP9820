## 一、一句话总览

本周两讲都"不难但重要"。**(1) 管理与指标——以覆盖率报告为例**：经理需要知道团队是否高效、怎样帮他们成功；麦格雷戈 X 理论（人逃避工作→控制+外在激励+测量）vs Y 理论（人主动担责→环境+自主+内在动机），敏捷假设 Y。指标（commit 数、测试数、代码行数、覆盖率）能显示趋势和红旗，但**一旦数字变成目标就有害**（"90% 覆盖率"命令 → 恐慌 → 廉价测试 → 质量不升）。健康用法：团队用指标检查改进自己的系统，管理层用它**开启对话而非记分**。现场演示 `pytest-cov` 终端与 HTML 报告，教读 Stmts/Miss/Cover/Missing，讲 statement 的含义与分支覆盖；AI 能快速生成测试和报告，也让"刷数字"更容易，**不要合并自己不理解的 AI 代码**。**(2) 面向可维护性的设计**：软件必然变化，可维护 = 能安全地快速改动；途径有测试、系统设计、代码设计（本课讲后者，在 TDD 的 Refactor 步骤发生）。**7 个设计问题**：唯一事实来源（DRY）、尽可能简单（KISS，clear > clever）、过度/不足设计（重复两次可以接受，不要无条件遵守原则）、相关模块靠近/无关模块分开（耦合、意大利面代码）、不要臆测未来需求（YAGNI）、遵循标准惯例（别用 C 写 Web）。**重构**=不改外部行为地重组代码，**没有强测试套件就别重构**。AI 能写能改，但设计决策与重构方向仍由人主导。结尾：Sprint 1 成绩已发（平均 HD 以上），Sprint 2/3 rubric 逐级更难。

## 二、按时间顺序的详细内容

### 03:46–10:50 开场与"经理的故事"

- 本周内容轻松、不难但重要；希望早点结束把时间还给大家做项目和其他作业。
- 这门课叫软件项目管理，前面讲的都是**敏捷**——团队人人参与管理。但还有 **manager** 这个角色（业界的经理、创业公司的 founder/co-founder）。今天第一讲：**如果你是经理/创业带队的人，能做什么让项目敏捷、给客户带来价值、高效、适应变化。**
- **故事第一幕**：你管理一个敏捷项目，每周/双周看 demo，新功能不断交付，一切正常；但慢慢 bug 越来越多，部署给用户后问题越来越多。你怎么办？
  - 学生：加追踪系统、看性能指标；加 **code review**。
  - 经理决定：加 code review + 加指标（既然功能交付了但 bug 多，就看**测试够不够、功能是否全被测**）。
- **故事第二幕**：几周后几乎所有功能都有测试了，测试数量暴涨。但**软件还是很 buggy**，并且因为测试太多，**测试变得很慢**。为什么？
  - 因为你要的就是"给我看有多少测试、是否覆盖所有函数"——团队被指标驱动，写了大量**琐碎测试**，目标从"软件稳定可靠"变成"每行代码都被覆盖"。**团队目标因经理的指挥而偏移。** 一开始没指标 bug 多，加了指标 bug 还多——根本问题没解决。
- 今天的主题：经理的角色、如何管理软件项目，以**覆盖率报告**作为指标的例子。

### 10:50–15:50 Theory X/Y 与指标的正确用法

- **In This Lecture**：经理需要知道团队是否高效、如何帮其成功；覆盖率报告是"指标可帮可害，取决于用法"的好例子。内容：测量式管理 vs 授权式管理；为什么覆盖率目标会被刷；如何安全使用（团队工具而非绩效分数）。
- **Theory X vs Theory Y（McGregor）**：90 年代前后有人研究大量软件公司，发现多数公司要么 X 要么 Y。X：假设人只想拿钱不爱工作 → 经理用控制、外在激励（"函数全覆盖就给钱/升职"）和大量测量（指标、报告、文档）。Y：假设人主动担责、希望项目成功 → 提供学习环境和支持，让人自主，用内在动机（"看多少用户在真正用你的代码"）。**敏捷假设 Y。**
- **指标可以有用**：commit 数一定程度上反映工作量，测试数一定程度反映测试彻底度，代码行数也能说明些东西——"说明一些但不是全部"。课件：显示趋势（交付加速/减速）、大红旗（事故/回滚增多）、指向该问的问题（"为什么这个服务这么脆弱？"）。
- **但要小心用**：数字变成目标就危险。"我让你们两天写 100 行代码，得到的是一堆质量差、跑不通的代码。"健康用法：**团队**用指标检查改进自己的工作系统（比如看有没有函数没被测试覆盖、里面藏着 bug）；**管理层**把它当对话的起点而非记分板——问"有没有函数还没测？"然后讨论：是时间太短？是不会写这种测试（blocker）？还是觉得暂时不需要？

### 15:50–21:20 覆盖率的两种含义与代码走读

- 用覆盖率报告作为具体例子：既是有用的工程反馈，又是容易被误用的指标——很多公司都在误用。
- **Coverage = 测试有多彻底。** 讲师问：你怎么知道测试够不够、该在哪加？学生：取决于功能数量。讲师：可以人工对照测试文件和实现文件逐个看；但就像 pipeline、Git 一样，**有工具能自动算吗？**
- **两种含义**：**Test coverage**——功能集有多少被测（通常人判断，"有加任务功能，也有加任务测试"）；**Code coverage**——测试期间多少代码被执行（可计算、给百分比）。今天讲后者。
- 打开上周的 Task Tracker：后端有显示/添加/删除三个故事；测试 `test_index_shows_tasks`、`test_index_loads`、`test_index_shows_initial_tasks` 全是显示任务——人工一看就知道 add/delete 没测（test coverage）。
- **Code coverage 告诉我们**：按执行的语句/行的百分比；最有用的是**指出没执行的部分**。三个测试都只 `client.get("/")`，所以 `add_task`、`delete_task` 里的语句明显没被执行。

### 21:20–26:00 pytest-cov 安装与终端报告演示

- pytest 不只能跑测试，还能算覆盖率：`pip install pytest-cov`（**Mac 用 `pip3`**）。讲师现场安装（已装过所以很快）。
- **建议把 `pytest-cov` 加进 `requirements.txt`**：上周 pipeline 的 `before_script` 从 requirements 装依赖，这样以后能把覆盖率加进 pipeline。
- 运行 `pytest --cov --cov-report=term-missing`：报告列出 `app.py`（19 语句，缺 8，58%，Missing 18-21, 25-27, 30）、`conftest.py` 100%、`tests/test_app.py` 100%、TOTAL 79%。
- 18–21 行是 add task 路由，25–27 行是 delete——正是没写测试的部分。"非常直观、很强大，我知道该在哪补测试了。"
- **为什么已有实现还要补测试**（不是 TDD 顺序）：以后重构/改代码，怎么知道行为没变？靠测试全绿。

### 26:00–35:30 HTML 报告演示、statement 的含义、Q&A

- `pytest --cov --cov-report=html` → 提示 `Coverage HTML written to dir htmlcov`；新目录里有 `index.html`，用 VS Code（或浏览器）打开。
- 总览表：Files / Functions / Classes 三个标签；总覆盖率 79%。点 `app.py`（58%，"几乎一半代码没被测试"）进入逐行视图：**绿色 = 测试时运行过；红色 = 缺失**（8 行）。
- "这些红行**可能**需要加测试——是否必要取决于你的判断。**不需要追求 100%**，有些行本来不需要测试，做项目时会遇到。指标本身（58%、红绿行）用得对很有帮助。"
- **什么是 statement**：讲师现场写代码——`a = 1` 是一个语句；跨 5 行的列表字面量也只是一个语句；把两个操作写在一起是**两个**语句（"做了两件不同的事"）。所以 `delete_task` 有 3 个语句全缺。
- **Functions 视图**（回答学生"顶部 Functions/Classes 是什么"）：按函数列覆盖率——`add_task` 4 语句全缺（0%）、`delete_task` 3 语句全缺（0%）、`index` 100%。函数多或大时用它找"哪个函数完全没测"。
- **学生问：pipeline 里能不能给每个 feature 出覆盖率报告？** 讲师坦言不知道怎么做、可能可以也可能不行，鼓励研究后下节课分享。**最低限度**：每个功能一个分支，跑该分支的覆盖率即等于该功能的覆盖率。
- 提醒：课件上有完整命令；Mac 记得 `pip3`。**Reading the coverage table**：Stmts / Miss / Cover / Missing 四列定义；有意思的永远是"缺了什么、你在不在乎那条路径"。

### 36:10–39:00 覆盖率命令的功能失调与分支覆盖

- **经典命令"所有代码必须 90% 覆盖率"** → 恐慌+截止日期不变 → 大量廉价测试（慢、脆、低信号）→ 时间浪费在等待和误报 → 质量交付不升。讲师："有些创业公司要求 90%，我不说它错，但要小心用，让团队追求好的覆盖而不是数字。**廉价测试不是没用，是有害。**"
- **为什么这种失调不可避免**：人的时间有限，花在刷数字上，就少花在没被计数的事上——内部质量、可维护性、真正的缺陷预防、客户成果。
- **覆盖率报告是什么/不是什么**：它是"测试期间执行了什么"的报告；用来找风险缺口、指导下一步加测试很好；当目标、KPI、绩效输入就危险。
- **分支覆盖**：有 `if/else` 逻辑时测试要覆盖所有情形。常见问题是只测 **happy path**；还要考虑**边界情况**——用户不会按你设计的方式用（"有时用得很奇怪"），例如上周空输入点 Add Task 该怎样？实现和测试都要考虑。多问"这个判断两边都测了吗""错误路径会怎样"。

### 39:00–46:08 AI 与覆盖率 / AI 与管理，第一讲收尾

- 反馈表里有同学提到 AI 在剧变工程领域（去年有公司大裁员）；要了解趋势，知道 AI 何时有帮助、何时有害。
- **AI 与覆盖率**：写测试比过去快得多；AI 能帮解读覆盖率报告（看不懂就问）；能建议让代码更可测的重构。但**盲用很危险**：讲师在上一门课见过学生用 AI 写大量廉价测试，只让数字涨，没真正测项目；头几天/几周没事，改动多了以后测试不能在弄坏东西时正确报警，长期越来越危险。
- **AI 与测量失调**：X 型（指标驱动）领导下，AI 让追踪更多数字、强推覆盖率目标更容易，也更容易造肤浅测试。**Y 型（授权式）**领导下，AI 帮经理减轻报告负担——从 commit / MR 信息起草 sprint 总结，把"交付了什么"变成给干系人的简短叙述，省下的时间用来看真实的工作、做 coaching。
- 讲师问 AI 对经理还有什么健康/危险用法（"AI 对我也是新东西"）。学生：不懂的可以问 AI 理解；但**用不理解的 AI 代码很危险**。讲师补充 Reddit 上开发者最后悔的事："合并了几行不理解的 AI 代码，把产品整个搞坏。" **教训：不合并任何没完全理解的 AI 生成代码。**
- **What this means for you**：AI 不会消除对深思熟虑测试的需求；它降低平庸产物（测试、指标、报告）的成本；你的优势是**先掌握好实践**再用 AI 强化它，并且不因为 AI 让某指标容易产出就去追它。

### 52:41–59:30 第二讲开场：为什么关心可维护性

- 休息期间讲师在 Moodle 论坛发本周 newsletter（本周继续在 Sprint 2 中实践 standups、meetings、issue board、Git、TDD、CI；**Sprint 1 成绩与反馈已在 Grades 发布**）。
- 第二讲：可维护性 / 重构 / 写可维护的代码，也不难。**为什么重要**：第一周就说软件项目一定会变——用户需求变（改功能、加功能）、经理/方向变、技术栈变、成员进出、或只是想让代码更优雅。要让改动安全，项目必须可维护、改起来风险低。
- Gru 表情包："给完美运行的代码加个小函数 → 全部崩溃 → 撤销所有改动 → 还是坏的"——"我见过很多版本，原因就是项目不可维护。"
- **软件随时间变化**，代码只增不减；敏捷小步交付→反馈→调整方向，代码难改就跟不上节奏——一开始赶工交付快，后面越加越慢。
- **可维护代码的好处**：加新功能不破坏旧的；修 bug 更快；通过 MR 协作（别人读得懂、能扩展）；和 AI 工具高效协作（代码乱 AI 也难帮）；新成员（包括**未来的你**）容易上手。"你希望项目被真实用户用、越来越好、理想上永远活着。"
- **可持续速度 > 原始性能**："速度"是安全做出一次改动有多快，不是打字快；可维护性让速度随代码库增长而保持，比原始性能更重要。
- **怎么做到**：① 测试（已讲）；② 系统设计（本课不涉及，自行探索）；③ **代码设计**（今天讲，并讲为什么 AI 只能辅助不能替代）。
- **代码设计**发生在写测试与写代码之间——对应 TDD 的第三步 **Refactor**：先测试、写最少代码通过，再回头重构并问自己 **7 个设计问题**（课件标题写 6，实际 7 条）。

### 59:30–01:03:50 Q1：唯一事实来源（DRY）

- 示例 `dry_dirty.py`：购物车每件商品单价×数量再打印总价，三件商品三段几乎相同的代码。学生："冗余。"讲师：商品会有 4、5……20 件，代码块无穷无尽；更糟的是**改动要改每一处**——把 "total" 改成 "cost"，讲师现场改出 `costs`/`coosts`/`cost` 三种不一致的手误："块一多就容易打错、漏改，因为你想改得一致。冗余的第二个问题是更容易出错。"
- **DRY（Don't Repeat Yourself）**：同一值/能力定义在多处，改动要改所有位置，极易漏改或不一致。"每一条知识在系统中应有唯一、无歧义、权威的表示。"（"这条不是绝对的，后面会讲。"）

### 01:03:50–01:08:30 Q2：尽可能简单（KISS）

- 每一行代码都要维护；行数越少要维护和测试的越少。已有 Python 库/函数能用就别自己写。**"你没写的每一行代码都没有 bug。"**
- **KISS（Keep It Simple, Stupid）**：系统简单时运行最好，复杂度与错误相关。**Clear code > Clever code**；"没有正常人喜欢本可以更简单的聪明代码"；别炫技。
- 交换两个变量三种写法投票：A 加减法不用临时变量；B 临时变量；C Python 的 `a, b = b, a`。选 B："多语言通用（C、JS 都一样），易懂"；选 C："易维护；项目用 Python 就用 Python 方式；很简单"。讲师：**B、C 都行看偏好，避免 A**——显得聪明但连未来的你都难维护。

### 01:08:30–01:15:30 Q3：过度设计还是设计不足

- 示例 `over_under_design.py`：登录后按角色（只有 admin、moderator 两种）发邮件。A：两个 `if` 各自 `send_email`；B：`MESSAGES` 字典 + 一行查表。
- 两轮投票、互相说服（"辩论课"）。选 A：结构清晰、可读、定义明确；只有两个角色没多余东西；角色多了字典那行会很长。选 B：行数少易维护；将来加角色更容易扩展。
- 讲师：**我也选 A**。"我理解选 B 的人——刚说过行数少更好维护。但这里 A **更易读、逻辑更清楚**。它和购物车不同：购物车可能 10、20 件；这里只有两个角色，最多再加一两个，而且以后可能想给不同角色发不同邮件。**没有对错**，看你更舒服哪种、也看场景（会不会加很多角色？）。"
- 课件：过度设计 → 为琐碎改动维护复杂抽象；设计不足 → 随范围扩大不断重构。**有时重复两次（仅两次）是 OK 的；无条件遵守原则是坏主意，可能把复杂度加回来。** "通常从设计不足开始，然后变'聪明'过度设计，最终找到自己的平衡——多练习。"

### 01:15:30–01:21:00 Q4/Q5：相关模块靠近、无关模块分开（耦合）

- 示例 `coupling.py`：方式一——`add_task`、`delete_task`、`format_task_list` 三个独立函数；方式二——`do_everything(tasks, action, text_or_index)` 一个函数做加/删并且无论如何都打印。
- **耦合** = 一段代码对另一段的依赖程度。相关组件紧耦合、无关组件松耦合。互相依赖的函数改一个很可能影响另一个；分开的改一个不影响另一个。
- "Sprint 2 还好，Sprint 3 功能更多更复杂时会发现工作互相依赖：'等 B 做完我才能开始'、'我的改动影响了 C'。本质无关的就分开，本质相关的放一起。"过度耦合 → **意大利面代码**。
- 为什么方式二是意大利面？学生：加/删/显示本可独立；函数越来越大。讲师：更难维护更难读；**打印/格式化逻辑与用户动作逻辑性质完全不同**，混在一起就有问题。

### 01:21:00–01:23:40 Q6：不要臆测必要性（YAGNI）

- "初学者**非常非常常见**的错误。"上周说过只写让测试通过的代码。"这行代码将来可能有用""这个 helper 现在只用一次但我确定以后会反复用，先抽出来"——都是在臆测未来，那个 helper 可能永远用不上。**只有真的看到需要才写，否则保持简单。**
- **YAGNI（You Aren't Gonna Need It）**：确定会用之前不加功能，去掉不必要的代码、减少维护。自顶向下：从高层抽象往下，避免先写可能永远没人用的底层工具函数。
- 问题："没人要之前该给 Task Tracker 加导出 PDF 吗？"——**不**。所有故事应来自 Sprint 1 的需求工程（访谈、市场调研、观察）；当时发现强需求就排优先级去做，没人要过就别做，否则只是冗余功能。

### 01:23:40–01:28:10 Q7：遵循标准惯例 / 重构

- "你会用 C 写 Web 应用吗？"有学生说 C 自己控制循环更高效。讲师：不是不能，是不符合惯例——用 C 的人少、资源和支持少（人们不用它也许有原因）；将来贡献者多半没有用 C 写 Web 的经验，但大多数人会 Python/JS。**没有任何一个人能独自写出业界规模的软件，再天才也写不出 YouTube 的体量，必须团队协作**——遵循惯例对你和其他贡献者都更易维护。范围从风格（常量大写）到库选择（Flask 流行、资源多、易贡献）。
- 回顾 `conventions_clear.py` 与只用一次却抽出 `is_valid_task` helper 的 "clever" 版本——"这就是我说的不必要的 helper。"
- **重构**：TDD 三步的第三步；在不改变外部行为的前提下重组现有代码——黑盒里在变（更快、更易维护、更易改），黑盒外行为不变。通常用于修正糟糕设计。**没有强测试套件时强烈不建议重构**——只有测试能告诉你改动没弄坏东西。

### 01:28:10–01:34:00 为什么有了 AI 仍然重要

- 讲师先不放课件让大家说：AI 对重构有帮助还是有局限？
  - 取决于项目和使用者；**你脑子里得有架构**，不能只说"重构这个"，要高层次地知道重构什么、怎么重构。
  - AI 会犯错。
  - **没人负责**。
  - 正面例子：后端从 JavaScript 框架**迁到 Python/Flask**，逻辑不变只换语言，AI 能帮。讲师："很好的想法，我没想过。风险？——整个项目换语言会产生**大量需要审查的 AI 代码**，审查工作量本身巨大；而我们不合并没完全理解的代码。"
- 课件：AI 基于**你的**代码库给建议，代码乱/重复/紧耦合 → AI 的重构更乱；人一开始就要给清晰结构，之后人和 AI 的改动都更安全。你仍要**读并批准每处改动**——所以要懂这些原则，才能判断好坏。AI 只实现你要的，不决定什么该简单/灵活；设计决策来自人；重构由人主导，"更好"由你定义。快速 AI 代码的技术债仍落在团队头上。**底线：AI 能写能改代码，但不替代好的设计；可维护性让代码库成为人和 AI 都能高效工作的地方。**
- 课后建议：开始**重构项目代码**，逐段问那七个问题（DRY、KISS、YAGNI、重复、过度/不足设计），但**重构任何一行前先确保有强测试套件**。

## 三、核心要点速览

1. **经理的职责**：知道团队是否高效、问题在哪、怎么帮他们成功——而不是下达数字目标。
2. **Theory X vs Y**：X = 人逃避工作 → 控制+外在激励+测量；Y = 人主动担责 → 环境+自主+内在动机。**敏捷假设 Y。**
3. **指标有用但要小心**：能显示趋势、红旗、该问的问题；**数字变成目标就有害**。团队用它自检改进，管理层用它**开启对话而非记分**。
4. **两种覆盖率**：test coverage（功能被测多少，人判断）vs code coverage（测试执行了多少代码，可量化）。最有用的是**没执行的部分**。
5. **工具链**：`pip3 install pytest-cov`（加进 `requirements.txt`）→ `pytest --cov --cov-report=term-missing` / `--cov-report=html` → `htmlcov/index.html`（Files / Functions / Classes，绿=已执行，红=缺失）。
6. **读表**：Stmts（可执行语句数；一个语句=一个有意义的操作，跨多行的字面量仍是一个）、Miss、Cover、Missing（行号）。
7. **不追求 100%**；已有实现也要补测试（为将来重构护航）；覆盖边界/错误路径，不只 happy path；关注**分支覆盖**。
8. **"必须 90%" 命令的必然失调**：恐慌 → 廉价测试（慢、脆、低信号）→ 质量不升；时间花在刷数字上就不花在内部质量、可维护性、真正的缺陷预防、客户成果上。
9. **AI 与指标**：AI 让写测试/出报告更便宜，也让刷数字更容易；Y 型经理可用 AI 从 commit/MR 起草 sprint 总结、省时间做 coaching。**永远不合并没完全理解的 AI 代码。**
10. **可维护性 = 能安全地快速改动**；"速度"是安全改动的速度而非打字速度；可持续速度 > 原始性能。途径：测试、系统设计、**代码设计**（TDD 的 Refactor 步骤）。
11. **7 个设计问题**：① 唯一事实来源（DRY）② 尽可能简单（KISS，clear > clever，没写的代码没 bug）③ 过度/不足设计（重复两次可接受，别无条件守原则）④⑤ 相关靠近、无关分开（耦合、意大利面代码）⑥ 不臆测未来（YAGNI，功能来自需求工程）⑦ 遵循惯例（流行方案资源多、他人易维护；软件是团队活）。
12. **重构** = 不改外部行为地重组代码；**没有强测试套件不要重构。**
13. **AI 与设计**：AI 基于你的代码库给建议，乱进乱出；设计决策、"什么叫更好"、审批每处改动都由人负责。语言迁移等场景 AI 有用，但审查量巨大。
14. **行政**：Sprint 1 成绩已在 Moodle Grades（平均 HD 以上），本周 class 问 tutor 反馈；Sprint 2、3 rubric 逐级更难，持续打基础。
