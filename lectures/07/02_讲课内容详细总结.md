### 00:27–00:46 Lecture 7.1 Persistence
- **演示**（`main` 分支的 Task Tracker）：添加任务「persistence」，刷新还在，**重启服务器就没了**——任务列表只在内存里。这样的 tracker 不能用；理想是任务一直在，直到点 Delete。若有 deadline、assignee、多用户，这些也都要保存 → persistence。
- **数据层**：分层方式因人而异，示例四层——Interface（通常无状态，如页面缩放丢了没关系）、Business Logic（stakeholder 定义的行为，如点按钮回上一页）、Services（购物车、「用户可添加任务」）、Data Layer（存用户、任务等，即 database）。
- 现场问是否用数据库：有的用有的不用。研究生背景多样，都没问题。今天介绍最简单的**文件式持久化**，对学生项目够用；已用数据库的也可学一种更简单的方式。
- 三种存储：内存（重启即丢）、文件（类比：笔记本里的讲义 PDF 文件夹，重启还在——这就是一种数据库）、SQL/NoSQL（数据关系复杂时用；门槛更高、性能更高）。**本项目文件系统足够**。想学 SQL → COMP3311。
- **Persistence 定义**：程序状态比进程活得久，重启后数据还在；本课程 = 存到磁盘。
- **演示 `persistence` 分支**：添加任务 → 停止/重启服务器 → 刷新 → 任务还在。代码只多了约 5–6 行：
  - JSON 文件是什么：不能运行、只存数据的文件（像 Google Doc/Excel；YAML、Markdown 也是），但 JSON 与编程语言交互很强——轻松变 Python list/object 或 JS object。可存 list 也可存对象。
  - `import json`；`from pathlib import Path`（要知道读写位置）；`DATA_FILE = .../tasks.json`（名字随意）；文件存在则 `json.load` 读为 Python list（JSON 内容只是字符串，load 后才能增删改）；`save()` 用 `json.dump` 写回；在 add/delete 后调用 `save()`。
  - 直接手改 `tasks.json` 加「test」，重启后页面出现——**数据变化不只来自前端 UI**，也可来自后端、邮件触发、点赞计数等，很强大。
  - 数据多时可有 `tasks.json`、`users.json` 等多个文件。
- **Q：想保存图片？** 学生：存文件地址、存外部 URL。讲师：都可以，选最适合的；注意**图片大小**；很多项目会需要（如头像）。
- 觉得 SQL 太复杂 → 用文件式持久化，简单快速。**Persistence 非必须**，取决于 story，但估计大多数项目都需要。

### 00:55–01:05 Lecture 7.2 复杂度的定义
- 之前多次说要避免复杂度；今天讲如何**定义、度量**复杂度，以及何时需要处理。
- **No Silver Bullet（Brooks, 1986）**：本质复杂度（问题固有，如客户要 30 个功能；不可去除，用好设计管理——低耦合高内聚）vs 偶然复杂度（非固有，如特定格式数据的生成/解析；可用库、标准缓解，难以完全去除）。
- **Quiz 1**：A 1 人、B 几人、D 1 人、C 0 人。答案 **B**。A 糟糕设计可去除 → 偶然；D 开发者无意引入可部分去除 → 偶然；C 可换语言。
- **开放问题 1**：没有算法式流程，**靠人判断**（你最了解自己的项目：这是 stakeholder 要求还是设计所致）；通过抽象/领域建模区分。例：薪资系统税务逻辑是本质（法律），手动数据库处理是偶然。边界随技术移动：C 语言手动管理内存曾是本质，现在 Python/JS 自动管理，若仍手动就是偶然。
- **开放问题 2**：很大比例（50–70%+），Microsoft/Google 的系统也如此。来源：人与流程（协作不善）、文档过载、工具过载（13 或 30 个环境变量）。
- **开放问题 3**：未来能去除多少？「I don't know, you may tell me in the future.」
- **Sprint 3 任务**：识别项目中的本质与偶然复杂度并说明理由。给一分钟思考；不清楚就与队友讨论。

### 01:05–01:13 为何/如何度量：Coupling 与 Cohesion
- **为何度量**：改善可维护性（找出过复杂的组件处理，OK 的不管）；估算工作量（重构高复杂度模块要多留时间——依赖多、人多）；评估质量；指导重构与设计。
- 本课三种度量：Coupling、Cohesion、Cyclomatic Complexity（实际更多）。
- **Coupling**：学生答「依赖少；相关放一起，不相关分开」。依赖多则改一处牵动多处 → 追求松耦合。为何前后端松耦合？学生：后端数据逻辑多、可能出问题、后端不再需要的东西不该影响前端。讲师：逻辑分离，改动互不牵连。
- **Cohesion**：相关元素放一起 → 高内聚好。学生例：相关功能分组；点 checkbox 删除任务的逻辑代码放在一起。
- **Quiz 2**：全场选 **B**（低耦合 = 模块间依赖少），正确。
- **Sprint 3 任务**：检查代码库找 coupling/cohesion 需重构之处。**技巧：看自己的代码难发现问题，看别人的容易——小组互相重构对方代码。**

### 01:13–01:31 Cyclomatic Complexity
- 分支复杂度（if/else/for/while，逻辑分支不是 Git 分支）；研究发现分支是函数复杂度主要来源；测试角度每个分支都要测。
- 核心：每个决策点增加执行路径；`if/else` = 2。公式 **V(G) = e − n + 2**（边 − 节点 + 2）。
- **Example 1**（if/else）：4 − 4 + 2 = 2。
- **Example 2**（if / else-if）：讲师用 Teams Whiteboard 现场画，漏了 B→E、D→E，翻答案发现「所有分支都汇到结束节点」。6 − 5 + 2 = **3**。「It's okay to be confused sometimes.」
- **Example 3**（while）：A→B→A，A→C；3 − 3 + 2 = 2。
- **Example 4**（`day_to_year`，while 内嵌两层 if）：让大家自己画（有白板笔可上台）。讲师自己画时迷路（「Oh my god, I'm so lost」「I need help」），一位学生上台一起完成：关键是 `days > 366` 为假、以及两个赋值块执行完都**回到 while 判断**。有同学几分钟就算出 **4**；答案 8 − 6 + 2 = **4**。「看答案没问题，自己做才发现复杂。」
- **Example 5**：重构后同样功能 7 − 6 + 2 = 3 → 重构可降低圈复杂度。可课后练习。
- **Sprint 3 任务**：找一个分支最多、最复杂的函数，算圈复杂度并尝试降低；有挑战，卡住正常，小组讨论；**不需要算所有函数**。

### 01:31–01:34 Usage / Drawbacks / 工具
- 上限争论：10 或 8。没有超过就没事。
- 缺点：① 假设非分支语句（赋值、加法）零复杂度，不真实；② 鼓励拆函数，但拆分不一定更易懂。**天生复杂无法降低的函数可以保留**，报告里写明「complicated by nature」，不拆分也可以。
- 有语言相关的自动计算工具，但要理解公式和画图方法。
- Further reading（原论文、McConnell、ploeh 的反驳）。

### 01:34–01:38 回到 guideline §4.4 与结束
- 「addressing complexity」= 不是砍功能，而是**指出并处理**结构问题（essential vs accidental；重复逻辑、边界不清）。
- 报告内容：① coupling/cohesion 的重构（不需要全面重构每一行，做一些练习即可）；② 圈复杂度：挑一个最复杂的函数算并降低；③ 把复杂度当项目管理问题：建 issue「refactoring for complexity」，细分 cohesion/coupling/cyclomatic 并指派；**小而可审的 MR 优于大改**；④ 需要持久化的项目按 checklist。
- 报告是 markdown 文件，**可分多次 commit** 完成。

## 核心要点速览

1. **Sprint 3 = 交付**：Week 10 lab 正式 demo（10–15 min + 5 min Q&A，两位 tutor 平均分，全员发言，**全员出席否则 0 分**）；Week 10 周五 17:00 提交 GitLab `main` + Moodle portfolio。
2. **不要求部署**，localhost 即可；Week 9 后可选在论坛分享部署链接或 5 分钟视频。
3. **至少一个 meaningful 改进**；不按功能数量给分，讲清用户/问题/价值/决策。
4. **报告只有上限**：复杂度报告 1–2 页（`docs/REFACTORING_AND_COMPLEXITY.md`，含 essential vs accidental、coupling/cohesion、一次重构的圈复杂度，链接 MR/issue）；portfolio ≤1000 词。
5. **GenAI 可用但必须审核并声明**——AI 生成的低质量记录会拉低分数。
6. **Persistence** = 状态比进程活得久；本课程即存盘。对学生项目 **JSON 文件足够**：`json` + `pathlib`，启动 `json.load`，每次变更 `json.dump`；测试用临时文件；README 写清数据文件位置。
7. **复杂度两类**：本质（问题固有，用设计管理）vs 偶然（可缓解难根除，占现代软件 50–70%+）；区分靠人的判断，边界随技术移动。
8. **三种度量**：Coupling（松好）、Cohesion（高好）、Cyclomatic Complexity **V(G) = e − n + 2**；常见上限 8–10，仅作指导。
9. 圈复杂度缺点：忽略非分支语句；诱导无意义拆函数——天生复杂可保留并说明。
10. 实用技巧：互相重构对方代码更容易发现问题；把复杂度当项目管理问题（issue 细分、小 MR、说明 why）；报告可多次 commit。
11. 工具推荐：**diff-cover**（只算 diff 行覆盖率）。
12. Week 8 周一公假 → 录播；Week 9 最后一讲。
